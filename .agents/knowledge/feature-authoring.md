# Feature Authoring

Read this before creating or editing anything under `src/<id>/`. Behavior of a specific feature lives in its spec
(`openspec/specs/<id>/spec.md`); this file holds the conventions every feature follows. Spec format facts:
`.agents/knowledge/references.md` (Dev Containers).

## Layout

| Path                                 | Role                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- |
| `src/<id>/devcontainer-feature.json` | Metadata and options; `id` equals the folder name                      |
| `src/<id>/install.sh`                | Entry point, executable, runs as root at image build time              |
| `src/<id>/NOTES.md`                  | User-facing notes, merged into the generated README                    |
| `src/<id>/README.md`                 | Generated by `just docs` from the two files above — never edit by hand |
| `src/<id>/scripts/`                  | Optional helpers `install.sh` calls                                    |

Everything inside `src/<id>/` ships in the published artifact; nothing outside it does. Start a new feature with
`just new-feature <id>` once its OpenSpec change exists, then replace every TODO.

## Metadata

- `id`: lowercase words joined by hyphens, equal to the folder name. Never change it after the first release; rename
  with `legacyIds` instead (below).
- `name` and `description` are required; `documentationURL` points at
  `https://github.com/hoshiori-dev/devcontainer-features/tree/main/src/<id>`.
- Options are `boolean` or `string`. `enum` restricts values; `proposals` suggests them and allows others. Every option
  has a default. Option names are camelCase; `install.sh` receives them as environment variables, upper-cased with
  non-word characters turned into `_` (`installTools` → `INSTALLTOOLS`).
- `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, and `init` widen what the container may do: add one
  only when the approved design names it.

## install.sh

- Use `#!/usr/bin/env bash` with `set -euo pipefail` when every image in the compatibility list ships bash; otherwise
  POSIX `#!/bin/sh` with `set -eu`.
- Detect the distribution from `/etc/os-release` and fail with a clear message on an unsupported one.
- Non-interactive always (`DEBIAN_FRONTEND=noninteractive`); clean package-manager caches at the end.
- User-scoped setup targets `_REMOTE_USER` / `_REMOTE_USER_HOME` (also `_CONTAINER_USER`, `_CONTAINER_USER_HOME`), never
  a hard-coded user.
- Download only from the sources listed in the spec, over HTTPS, and verify every download — a published checksum or a
  signature whose key is pinned by fingerprint. No `curl | sh` from an unpinned source.

## Idempotency

Every feature must succeed when installed twice on the same image, including with different options the second time; the
duplicate test proves it (`.agents/knowledge/testing.md`).

- Check before acting: skip an install when the requested version is already present.
- Overwrite files instead of appending; guard any edit to a shared file (shell rc files, `/etc/profile.d`) with a marker
  check so a second run adds nothing.
- Create users, groups, and directories only if missing (`id -u`, `getent`, `mkdir -p`); replace links with `ln -sf`.
- The spec states what a second install with different options does (for example: the later options win, or both
  versions coexist); `duplicate.sh` asserts exactly that.
- A feature that genuinely cannot be idempotent records `idempotencyExemption` with the reason in its compatibility
  list, and the approved design explains why.

## Dependencies between features

- Both `dependsOn` and `installsAfter` always use the full GHCR ref, including for features of this repository:
  `ghcr.io/hoshiori-dev/devcontainer-features/<id>:<major>` in `dependsOn`, the same ref without the tag in
  `installsAfter`. Never a local path (`./<id>`, `../<id>`): it resolves against the consumer's `.devcontainer/` folder,
  so it breaks in tests and after publishing. `just validate` rejects it. Tests resolve full refs to this checkout on
  their own (`testing.md`).
- Use `installsAfter` when only ordering matters; `dependsOn` installs the dependency for the user.
- External features use their full ref with a major tag.
- A PATCH or MINOR change to a dependency needs no change in its dependents: they reference the floating major tag. Only
  a MAJOR bump of the dependency means updating every dependent's reference and bumping those dependents too. CI
  re-tests every dependent of a changed feature either way.

## Versions

Every change under `src/<id>/` raises that feature's `version` (CI enforces it). New features start at `1.0.0`. A
behavior change — an option, a supported image, what install does — travels in one PR with its OpenSpec change (the spec
delta), the tests that cover it (a scenario for a new option), the bump, and the README regenerated by `just docs`.

| Bump  | When                                                                                                               |
| ----- | ------------------------------------------------------------------------------------------------------------------ |
| PATCH | Fixes, NOTES.md edits, upstream URL changes with identical results                                                 |
| MINOR | A new option, a newly supported image, backward-compatible new behavior                                            |
| MAJOR | An option removed or renamed, a default changed, an image dropped, install locations moved — the PR title gets `!` |

## Renaming and retiring

- Rename: new folder and `id`, the old id in `legacyIds`, and keep counting versions from the old id; never restart at
  `1.0.0`.
- Retire: `deprecated: true` hides the feature from the index and tools; removing a capability goes through an OpenSpec
  change that retires its spec.
