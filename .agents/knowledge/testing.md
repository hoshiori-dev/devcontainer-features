# Testing Features

Read this before writing or editing anything under `test/`, when running feature tests locally, or when CI tested
something unexpected (or skipped something you expected). CI job map: `.agents/knowledge/github/checks.md`.

## Layout

| Path                                     | Role                                                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `test/<id>/compatibility.json`           | The images the feature supports — required; schema `test/compatibility.schema.json`                                |
| `test/<id>/test.sh`                      | Autogenerated test: default options, run on every compatibility image                                              |
| `test/<id>/duplicate.sh`                 | Install-twice test: non-default options, then defaults; option values arrive as `<OPTION>` and `<OPTION>__DEFAULT` |
| `test/<id>/scenarios.json` + `<name>.sh` | Specific option combinations; `test/<id>/<name>/` holds extra files (a Dockerfile for a `build` scenario)          |
| `test/<id>/_feature/`                    | Only in a test run, never in the repository: a copy of `src/<id>/`, so a scenario script can run the installer     |
| `test/_global/`                          | `scenarios.json` + `<name>.sh`: scenarios that install several features together                                   |
| `test/canary.json`                       | `{"features": [...]}` — the features CI runs when the test infrastructure itself changes                           |

Test scripts run inside the built container: `source dev-container-features-test-lib`, then `check "<label>" <command>`
per assertion and `reportResults` last. A POSIX `sh` test sources `test/<id>/checks.sh` instead, a stand-in with the
same interface, because the library is bash; `just new-feature <id> --posix` generates it.

## Test intent and readability

Tests run known logic in declared environments with expected inputs; they are not public input-processing products. Make
setup, the action under test, and assertions easy to compare with the intended behavior. Add defensive handling only
when the expected environment requires it or it clarifies the test's meaning. Invalid input is appropriate when it is
the explicit subject of a test. Write test scripts as `.agents/knowledge/shell-style.md` says. Security review of test
execution follows review-guidance.md.

## Scenario names

A scenario whose subject is an installation that must fail is named `fail_*`; every other scenario is named `test_*`.
The name is the key in `scenarios.json`, the script's file name, and the folder of extra files. The prefix names the
subject, not the outcome: a `fail_*` scenario passes like any other, and what fails is a run of the installer inside its
script (Running the installer), so each `fail_*` script asserts at least one run that exits non-zero. A script that
holds both kinds of assertion takes the prefix of what it exists to show. `test.sh` and `duplicate.sh` keep the names
the CLI fixes.

The five package-list installers follow the rule. The other features and `test/_global` keep their names until #117
renames them and adds the `just validate` rule; a scenario added to one of them before that follows the rule already.

## Running the installer

A failing `install.sh` fails the image build, so no script runs, and the CLI installs a feature once per scenario. A
scenario that must assert a failure, or a second installation with other options, therefore installs the feature through
the CLI with options under which it succeeds (for a package-list installer, an empty list) and its script runs the
installer itself:

- A test run copies `src/<id>/` of the checkout to `test/<id>/_feature/` (`scripts/lib/stage.ts`), and the CLI copies
  the test folder into the container, so the script finds `_feature/install.sh` beside itself. The copy is for running
  the installer: its `devcontainer-feature.json` is the unrewritten source and resolves no reference. `_feature` is a
  reserved name; `just validate` rejects a path or a scenario of that name.
- The script runs the installer as root — through `sudo` when the scenario's `remoteUser` is not root — as often as it
  needs, with the options as environment variables (`packages` arrives as `PACKAGES`), and asserts the exit status, the
  output, and the state of the container after each run. A failing check names the entry or list it ran with and shows
  the installer's output. Each feature keeps the run and the assertions its scripts share in one helper file in its test
  folder (`test/apt-packages/installer.sh`).
- The run does not pass through the CLI's wrapper: the script sets the environment variables itself, and `_REMOTE_USER`
  and the other variables the CLI provides are absent unless it sets them. The autogenerated test and the scenarios that
  install through the CLI keep covering the wrapper.
- Preparation is the script's or the scenario's: the script changes the container before a run (a repository, a stub on
  `PATH`, a server on a loopback address); a container without a network is `"runArgs": ["--network=none"]`; an image
  that must hold something before the feature is installed, or an image outside the compatibility list, is a `build`
  scenario with a Dockerfile. No scenario gains `privileged`, `capAdd`, `securityOpt`, `mounts`, or an `entrypoint` for
  it.
- Checks that share a preparation share a scenario: every scenario costs an image build.

What it cannot express: a failure of the image build itself, a container whose network changes while the script runs,
and a check that needs more than one container or something on the host. Such a check goes to a maintainer before it is
dropped or kept as a manual check.

## Compatibility list

`compatibility.json` is the single source of the images a feature supports; its spec refers to it and never lists
images. Each entry is `{"image": "…"}` with optional `"arch": ["amd64", "arm64"]` (default amd64; arm64 runs on an arm64
runner) and `"remoteUser"`. Optional top-level `"scenarioArchitectures"` selects architectures for all feature scenarios
(default `["amd64"]`); it is a nonempty, unique array of `amd64` and/or `arm64`. Glab declares both architectures to
retain its version scenario coverage. Every scenario `image` must be listed for every selected architecture by the owner
and every in-repo feature it installs; `build` scenarios are exempt. Global scenarios run on amd64 and their images must
be listed for amd64 by every in-repo feature they install. Scenario architecture selection controls CI coverage and does
not change supported image/architecture pairs or require a version bump by itself. Adding an image or architecture is a
MINOR bump, dropping one MAJOR (`feature-authoring.md`); `just validate` checks the bump against the base.
`duplicate.sh` is required unless the list sets `idempotencyExemption`, which a maintainer approves.

## Running tests locally

Docker runs inside the dev container, so every CI test job can be reproduced:

- `just test <id>` — autogenerated + duplicate tests on each compatibility image of this machine's architecture, as the
  image's `remoteUser` when it names one; `--image <ref>` for one image, `--preserve` keeps containers, `--keep` keeps
  the staging directory. When no image lists this architecture it fails instead of passing with nothing run; pass
  `--image` to test one anyway.
- `just test-scenarios <id>`, `just test-global`.
- `just affected` — the plan CI will run for the current branch against `origin/main`.

## How CI selects tests

Container tests run only on pull requests, only for affected features, in parallel, and a new push cancels the running
set (`scripts/affected.ts`, `scripts/lib/repo.ts`):

1. A change under `src/<id>/` or `test/<id>/` affects `<id>`.
2. A `src/` change also affects every feature that installs the changed one through `dependsOn` or `installsAfter`,
   transitively — their installed result changes too — and every feature whose scenarios install one of those. A feature
   reached only through its scenarios does not pass the change on: its own artifact is unchanged. A change only under
   `test/<id>/` changes nothing users install, so it stops at `<id>`.
3. A change to `test/_global/`, or a `src/` change that reaches a feature the global scenarios install, runs the global
   scenarios.
4. A change to the test infrastructure (the paths in `INFRA_PATHS` in `scripts/lib/repo.ts`) adds the canary features,
   without their dependents, and runs the global scenarios, so both test paths go through the changed pipeline.
5. Each affected feature gets one job per compatibility image and architecture, plus one scenario job per selected
   scenario architecture when it has scenarios. More than 256 jobs in one matrix fails `plan`: split the PR.

## Local dependency resolution

`devcontainer features test` would install an in-repo dependency from GHCR — the old, published version.
`scripts/test_feature.ts` therefore starts a throwaway OCI registry (`registry` image pinned in the script) on a free
`localhost` port, stages a copy of `src/` and `test/` in which every in-repo reference — `dependsOn`, `installsAfter`,
scenario and global scenario keys — names that registry instead of GHCR (`scripts/lib/stage.ts`), publishes the staged
features there, runs the tests, and removes both — also when interrupted, though a test container the CLI had started
may remain (`docker ps -a`). A bare scenario key (`node`) becomes `<registry>/<repo>/node:<major>`. Only what the test
needs is staged and published: the feature under test (or the global scenarios' features), the features its scenarios
install, and their `dependsOn` / `installsAfter` closure — a broken unrelated feature cannot fail the job.

References stay OCI refs, so the CLI treats them as it does for users: a dependency a scenario also installs is
installed once, `installsAfter` orders against it, and `:<major>` resolves only when it is the dependency's current
major. A local folder would break all three. A dependent is always tested against the dependency in the same checkout;
the source always keeps full GHCR refs. The feature under test in the autogenerated and duplicate tests is still the
CLI's local copy (`./<id>`), which never collides with its dependencies. Needs docker, which the dev container and every
runner have.

## Choosing canaries

Keep `test/canary.json` at one or two fast, stable features, and include one with an in-repo `dependsOn` once such a
pair exists, so infrastructure changes exercise staging too. It is empty until the first features land. Replace a canary
before retiring it (`just validate` rejects unknown ids).
