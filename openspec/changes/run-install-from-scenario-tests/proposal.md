# Proposal

Implements [#50](https://github.com/hoshiori-dev/devcontainer-features/issues/50).

## Why

A scenario test cannot assert that `install.sh` fails: the failure stops the image build, so no check script runs. Nor
can it run the feature a second time with other options. Five features therefore carry host-side runners under
`test/<id>/` — `apt-packages`, `apk-packages`, `dnf-packages`, `pacman-packages`, and `zypper-packages`, eight files and
about 4,800 lines — that are run by hand, with their output pasted into a pull request. CI runs none of them,
`just
check` neither type-checks nor lints them, and `.agents/knowledge/testing.md` does not list them. Every refusal,
every expected failure, and every second installation with a different list of those features is unchecked on each pull
request after the one that added it. The five installers' specifications are archived, which was the condition the issue
set for starting.

## What Changes

- A scenario test script can run the `install.sh` of the feature it tests, from this checkout, inside the scenario's
  container, as often as it needs and with the options it chooses, and assert the exit status, the output, and the state
  of the container after each run.
- CI runs those assertions in the scenario jobs it already has, for each affected feature. No job, workflow, or `just`
  recipe is added.
- The checks the five installers' host-side runners perform become scenario tests, and the eight runner files are
  deleted.
- `.agents/knowledge/testing.md` documents the test type: how a scenario runs the installer itself, what it can prepare
  beforehand, and which checks it cannot express.
- The name under which the installer reaches a test is reserved: `just validate` rejects a repository that commits a
  file or names a scenario there.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. This change edits the harness and tests only (`skip_specs: true`).

## Impact

- Files: `scripts/lib/stage.ts` and its tests; `scripts/validate.ts` and its tests; `test/<id>/` of the five installers
  (new scenarios and scripts, the eight `direct_checks.ts` and `control_checks.ts` files removed, comments that name
  them corrected); `.agents/knowledge/testing.md`; `CONTRIBUTING.md` if its overview of the tests no longer holds.
- Feature ids touched: `apt-packages`, `apk-packages`, `dnf-packages`, `pacman-packages`, `zypper-packages`, under
  `test/` only. Nothing under `src/` changes, so no version is bumped.
- CI: `scripts/lib/` is test infrastructure, so this pull request runs the global scenarios besides the five features'
  jobs. The scenario jobs of the five installers run more scenarios from then on.
- Not touched: the host-side runners of `hf-cli` and `colab-cli`, added after the issue was written. Some of their
  checks need more than one container. They are left for a follow-up issue, which this pull request's description names.

## Acceptance

**Becomes true:**

- A scenario script of each of the five installers runs that feature's `install.sh` with an entry the specification says
  is refused, and its checks pass only when the run exits with the specified status, prints the refusal, and leaves the
  package database unchanged.
- With `src/apt-packages/install.sh` changed in the working tree so that it accepts one refused entry,
  `just test-scenarios apt-packages` fails on the check for that entry; the observation is recorded in this pull
  request's Validation section and the edit is discarded without being committed.
- A scenario script of each of the five installers installs one list and then another in the same container and asserts
  the result of the second run.
- No file matching `test/*-packages/direct_checks.ts` or `test/*-packages/control_checks.ts` exists.
- Every specification scenario that a deleted runner checked is named in the header comment of a scenario script that
  checks it, or is listed in this pull request's Validation section with the reason it could not be moved. A check that
  could not be moved stops the work until a maintainer decides (see the design).
- `git grep -n -e direct_checks -e control_checks -- test/ src/ .agents/ CONTRIBUTING.md` finds no line about the five
  installers.
- `.agents/knowledge/testing.md` lists the test type in its Layout table and states its limits.
- `just validate` fails, naming the path, for a repository that commits anything at the reserved name under `test/<id>/`
  or names a scenario after it.

**Stays true:**

- No file under `src/` or `openspec/specs/` changes; no feature's version changes.
- The feature a test installs through the CLI — in the autogenerated, duplicate, scenario, and global tests — is built
  and resolved as before: the staged references, the local registry, and the published set are unchanged.
- A test still runs only against this checkout: the installer a script runs is the one in the working tree the job
  checked out, never a published version.
- The repository holds one copy of each feature's sources. Nothing generated for a test run is committed.
- No scenario gains `privileged`, `capAdd`, `securityOpt`, `mounts`, or an `entrypoint` through this change.
- `ci-gate` and the job names in `.agents/knowledge/github/checks.md` are unchanged, and the `main` ruleset is not
  touched.
- Existing scenarios, `test.sh`, and `duplicate.sh` of every feature pass unchanged.
- `just check` passes, and shellcheck covers every new test script through `just lint`.
