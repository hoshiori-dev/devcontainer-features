# Proposal

Implements [#75](https://github.com/hoshiori-dev/devcontainer-features/issues/75), part of
[#52](https://github.com/hoshiori-dev/devcontainer-features/issues/52).

## Why

`dnf-packages` predates the shell style guide (`.agents/knowledge/shell-style.md`). Its failure messages give no
`<id>: error:` prefix and no fix, a failing `dnf install` ends the build without a word from the feature, the install
and the cache cleaning log nothing, and some tests hide their intent: they have no labels, or their result depends on a
pipeline's status. The #52 audit confirmed these items for this feature. Restyling now lands before the phase 2 and 3
work (#57, #62), which changes the same `install.sh`.

## What Changes

- `src/dnf-packages/install.sh` follows the shell style guide: header, layout, names, quoting, `main` with named steps,
  readonly constants and validated options, `log` and `fail`.
- Every failure the feature reports has the form `dnf-packages: error: <reason>; <how to fix it>`, and still names what
  the spec requires it to name: the option, the refused entry, or `dnf` with the supported distributions.
- A failing `dnf install` or `dnf clean` ends with status 1 and a feature message that states `dnf`'s exit status, after
  `dnf`'s own output.
- Header, messages, and log lines use the wording the five package-list installers share (#52).
- The feature logs one line before it runs `dnf install` and one before it cleans `dnf`'s cache.
- The missing-`dnf` message names the image's distribution when `/etc/os-release` gives one and a generic name
  otherwise, and no pipeline's status decides which.
- Every test script under `test/dnf-packages/` follows the shell style guide: one labelled check per behavior in the
  spec's words, and no assertion that depends on a pipeline's status.
- No option, accepted input, exit status of a validation failure, package source, or verification setting changes, so no
  Requirement changes and the change carries no delta spec (`skip_specs: true`).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. The `dnf-packages` behavior that its Requirements cover is unchanged.

## Impact

- Feature id: `dnf-packages`, PATCH bump from `1.0.0` to `1.0.1`. Every change under `src/dnf-packages/` bumps the
  version, and new log lines, reworded messages, and a feature message with status 1 after a failed `dnf install` or
  `dnf clean` are fixes without a new option, image, or behavior (`.agents/knowledge/feature-authoring.md`, Versions).
- Files: `src/dnf-packages/install.sh`, `src/dnf-packages/devcontainer-feature.json` (version only),
  `src/dnf-packages/README.md` (regenerated by `just docs`), and every `*.sh` under `test/dnf-packages/`.
- Unchanged: `src/dnf-packages/NOTES.md`, `test/dnf-packages/scenarios.json`, `test/dnf-packages/compatibility.json`,
  `test/dnf-packages/control_checks.ts`, `openspec/specs/dnf-packages/spec.md`, and every other feature.

## Acceptance

**Becomes true:**

- `shellcheck -o require-variable-braces,require-double-brackets` reports nothing on `src/dnf-packages/install.sh` and
  on every `*.sh` under `test/dnf-packages/`, and every line of them fits in 120 characters.
- The header of `install.sh` states what it installs and from where, that it runs as root at image build time, the
  environment variable each option arrives in, and why it is POSIX `sh`.
- Every failure message of the feature itself (not `dnf`'s own output) starts with `dnf-packages: error:`, starts its
  text in lower case, has no trailing period, and gives a reason and a fix.
- The missing-`dnf` failure exits with status 1 also when `/etc/os-release` is missing, unreadable, or not valid shell.
- A failing `dnf install` or `dnf clean` exits with status 1 and a `dnf-packages: error:` line, which states `dnf`'s
  exit status, after `dnf`'s output.
- A non-empty run logs one `dnf-packages:` line naming the entries and the `installWeakDeps` and `refreshPolicy` values
  in effect before `dnf install`, and one before `dnf clean` when `cleanup` is `all` or `packages`; an empty run logs
  one line without a trailing period.
- Every test script under `test/dnf-packages/` asserts through labelled `check` calls in the spec's words and ends with
  `reportResults`, and no assertion's result depends on a pipeline's status or on both dnf4's and dnf5's cache roots
  existing.
- `src/dnf-packages/devcontainer-feature.json` has version `1.0.1`, and `just docs` leaves the README unchanged.
- `just check`, `just test dnf-packages`, and `just test-scenarios dnf-packages` pass, and
  `test/dnf-packages/control_checks.ts` passes unchanged on every amd64 image of the compatibility list.

**Stays true:**

- No change to download sources, TLS, checksum, or signature verification: `dnf` still installs only from the
  repositories the image enables, with the image's signature and TLS settings, and the feature adds or changes no
  repository, key, or `dnf` configuration.
- Every Requirement and Scenario of `openspec/specs/dnf-packages/spec.md` still holds, and the spec's text is unchanged.
- The options' names, types, defaults, and `enum` values are unchanged, and `just spec-check` passes.
- Invalid controls, including explicitly empty ones, a refused entry, and a missing `dnf` still exit with status 1
  before anything changes, and an empty list still exits 0 also without `dnf`.
- The set of accepted and refused entries is unchanged.
- The feature still installs twice: the duplicate test passes on every image and architecture of the compatibility list.
- The supported images and architectures are unchanged.
