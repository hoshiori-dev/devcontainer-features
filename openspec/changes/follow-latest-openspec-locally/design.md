# Design

## Context

See [proposal.md](proposal.md) for motivation and acceptance.

Read from the published packages of OpenSpec 1.13.2 and 1.14.1 (`dist/core/validation/validator.js`), and from runs of
1.14.1 against `main` on 2026-10-15:

- The limit is the constant `MAX_REQUIREMENT_TEXT_LENGTH = 500`. 1.13.2 reports a main-spec requirement over it at level
  `INFO`; 1.14 reports it as `WARNING`, and also checks the text of each ADDED requirement in a change's delta the same
  way, with the message prefixed by `ADDED "<name>":`. MODIFIED requirements are not checked.
- In strict mode an item is valid only with no error and no warning. OpenSpec offers no option, configuration field, or
  environment variable that disables or re-levels one rule.
- `openspec validate --all --strict --json` prints every item with its issues (`level`, `path`, `message`) and a
  summary. On `main` it reports 115 issues over the 14 specs, all of them this one warning.
- 1.14's spec-driven schema (`schemas/spec-driven/schema.yaml`) instructs the author to keep each requirement's
  description to 500 characters, so OpenSpec's propose flow pushes agents to shorten requirements.
- With 1.14.1, `openspec init --tools claude` produces generated skills and commands that differ from the committed ones
  (generated by 1.13.2); the Option requirement check passes. No active change existed, so the archive path of that
  check was not exercised.
- 1.14.2 was published to npm on 2026-10-15 at 00:17 UTC. Deno 2.9.7, CI's and the dev container's version, refuses by
  default to install an npm version younger than 24 hours (minimum dependency age), and `npm:<pkg>@latest` then resolves
  to the newest version old enough. The dev container's "newest" OpenSpec is therefore the newest release at least a day
  old.

## Goals / Non-Goals

**Goals:**

- Exactly one validation finding is exempt: a message matching `Requirement text is very long (>N characters)`, with or
  without the `ADDED "<name>":` prefix. Every other error or warning of any item fails the check and is printed with its
  item and path. Checked by unit tests over recorded `--json` output: only long-requirement warnings pass; an added
  other warning, an error, or an unparsable output fails.
- The check never relaxes more than strict mode does today: `INFO` findings are ignored as before, and a release that
  renames the message makes the finding fail again rather than pass silently. Checked by a unit test with a changed
  message.
- The release lookup never changes the exit status: a newer release, the registry being unreachable, and an unexpected
  response each print one line at most. Checked by unit tests with the lookup replaced.
- The lookup compares against releases Deno would install: the registry's `latest` tag counts only once it is older than
  Deno's default minimum dependency age, so the warning never names a version the pin cannot use yet. Checked by a unit
  test with a fresh `latest`.
- CI's pin is read from `.github/actions/setup-tools/action.yml`, the one place it lives; the script parses it, and a
  pin it cannot find fails the check. Checked by a unit test and by the CI run of this branch.
- The generated-file comparison runs exactly when the installed `openspec --version` equals CI's pin. Checked by running
  `just spec-check` with the pinned version and with another one.

**Non-Goals:**

- Pinning OpenSpec in the dev container, or making local and CI versions equal by any other means.
- Opening issues or pull requests automatically when the pin falls behind.
- Shortening or splitting existing requirements.
- Tracking releases of Deno, just, or the devcontainer CLI; Dependabot covers the actions, and the rest stay as they
  are.
- Changing the `src/openspec` feature or its tests.

## Decisions

### Filter OpenSpec's JSON output instead of patching OpenSpec or validating without `--strict`

`just spec-check` runs `openspec validate --all --strict --json` from `scripts/check_openspec.ts` and judges the issues
itself. Validating without `--strict` would let every warning through, not one rule. Patching or wrapping OpenSpec's
validator would depend on its internals and on how Deno installs it. Lowering the limit is not possible: the constant is
not configurable. Reading the JSON keeps strict mode for every other rule and depends only on OpenSpec's documented
output.

The validation moves from the justfile into the script, ahead of its other checks, so a single command reports
everything and the version line comes first.

### Compare the installed version with CI's pin, not with `generatedBy`

OpenSpec writes `metadata.generatedBy` into each generated skill. Using it to decide whether to compare generated files
would hide a forgotten regeneration on a branch that raises the pin: the installed version would equal the new pin while
the files still name the old one. Comparing with CI's pin runs the comparison exactly where it is meaningful, and keeps
the check on a version the project owns rather than a field of OpenSpec's file format.

### Warn about a newer release, never fail

The maintainer decided that the dev container follows the newest release, that a CI pin falling behind is reported but
does not fail, and that whoever sees the report opens an issue or a small pull request raising the pin. A failing check
would turn every OpenSpec release into a red CI on unrelated pull requests. In GitHub Actions the warning is a
`::warning::` annotation so it shows on the run's summary; locally it is a line on stderr. Raising the pin is a
dependency bump, which carries no OpenSpec change (`spec-workflow.md`, Scope of specifications).

Rejected: a scheduled workflow that opens an issue on each release — more automation with write access than the drift
warrants.

### Counter the schema's instruction in the project's rules

The project's `rules.specs` in `openspec/config.yaml` gain one rule: a requirement may exceed 500 characters when its
behavior cannot be stated completely in fewer, and information is never dropped to fit. Without it OpenSpec's propose
flow would keep instructing agents to shorten requirements the check now accepts.

## Risks / Trade-offs

- [A later OpenSpec release adds another strict finding] → local `just check` fails before CI does. That failure is the
  signal to look at the release; the release warning says what to do, and checks.md says so.
- [OpenSpec renames the long-requirement message] → the exemption stops matching and the check fails, visibly; the
  pattern is updated with the pin.
- [The registry lookup slows or breaks the check] → it is one request with a short timeout, and any failure is one line,
  not a failed check.
- [1.14 changes behavior the Option requirement check relies on (archive applying deltas, MODIFIED replacing a whole
  requirement, tables kept)] → re-verified on 1.14.2 before the pin is raised, with an active change carrying deltas;
  the comments naming the verified version are updated.
- [1.14.2 is younger than Deno's minimum dependency age when the pin is raised] → it is not by the time this change is
  implemented; if a newer release is the newest installable one then, the maintainer decides whether the pin follows it.
