# Proposal

Implements [#22](https://github.com/hoshiori-dev/devcontainer-features/issues/22).

## Why

A dev container on Alpine that needs a few extra system packages today needs a Dockerfile, or a broader feature that
also adds repositories and configures the system. The collection has no feature that only installs a list of packages
with `apk`. `apk-packages` is one of five atomic installers, one per package manager (`apt-packages`, `dnf-packages`,
`apk-packages`, `pacman-packages`, `zypper-packages`), which share one option shape and one script skeleton, and each of
which keeps its package manager's own behavior.

## What Changes

- A new feature `apk-packages` installs the system packages named in one option with `apk`, from the repositories the
  image already configures, and nothing else: no repositories, keys, or apk configuration of its own. Its contract is
  `specs/apk-packages/spec.md`.
- The repository's root `README.md` lists the feature under "## Features": one row with the id `apk-packages` linking to
  `src/apk-packages/` and a one-sentence description. If it is the first row, it replaces the line "No features have
  been published yet."

## Capabilities

### New Capabilities

- `apk-packages`: installing a list of system packages with `apk` from the image's configured repositories.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `apk-packages`, new, first published at version `1.0.0`. No other feature changes, and none
  depends on it, so CI tests only `apk-packages`.
- Files: `src/apk-packages/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/apk-packages/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` with its
  scenario scripts, and the direct checks named in `design.md`, Test plan); `openspec/specs/apk-packages/spec.md`,
  created when the change is archived; the root `README.md`, one row under "## Features" (distinct from the generated
  `src/apk-packages/README.md`).
- Supported images: the planned compatibility list is in `design.md` (Supported images); `test/apk-packages/`
  `compatibility.json` becomes its source of truth.
- No script, workflow, test infrastructure, or knowledge file changes. `test/canary.json` is not touched; whether
  `apk-packages` joins it is left to the maintainer.

## Acceptance

**Becomes true:**

- Every scenario in `specs/apk-packages/spec.md` passes in the test named for it in `design.md` (Test plan), and the
  PR's Validation section names each scenario with its test, image, architecture, and result:
  - scenario tests (`just test-scenarios apk-packages`) run in CI on amd64, each on the image its `scenarios.json` entry
    names;
  - the autogenerated and install-twice tests (`just test apk-packages`) run in CI on every image and architecture in
    `test/apk-packages/compatibility.json`;
  - the direct checks under `test/apk-packages/` run locally on every amd64 image in that list and on the pinned images
    outside it that `design.md` (Test plan) names, and their output is recorded in the Validation section; CI does not
    run them.
- The issue's acceptance sketch is covered by the scenarios "Listed packages are installed", "Image without apk fails
  clearly", and "Different list on the second install".
- `test/apk-packages/compatibility.json` lists exactly the images and architectures planned in `design.md`.
- `src/apk-packages/devcontainer-feature.json` has version `1.0.0` and a single option, `packages`; `just check` passes,
  including the README generated by `just docs`.
- The root `README.md` has, under "## Features", exactly one row for `apk-packages`, whose id links to
  `src/apk-packages/` and which describes the feature in one sentence; the line "No features have been published yet."
  is gone.

**Stays true:**

- The feature fetches nothing itself: `install.sh` contains no URL and no download tool, and every package comes from
  the repositories configured in the image.
- The feature never disables or weakens signature checking and itself adds, removes, or edits no repository, key, or apk
  configuration file (scenarios under "Repository authentication stays in effect").
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, or lifecycle commands.
- No file outside `src/apk-packages/`, `test/apk-packages/`, `openspec/`, and the root `README.md` changes; every
  required check passes on the PR.
