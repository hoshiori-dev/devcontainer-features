# Proposal

Implements [#150](https://github.com/hoshiori-dev/devcontainer-features/issues/150).

## Why

Developers who target HPC systems build and test their containers with Apptainer, and the local Slurm of the `slurm`
feature can run job steps inside such containers only when a runtime is installed next to it. Installing Apptainer by
hand in a dev container is error-prone: it needs the unprivileged, non-setuid build, a package source that differs per
distribution, and container security settings without which user namespaces, and so every `apptainer exec`, fail.

## What Changes

- A new feature `apptainer` installs Apptainer in its unprivileged, non-setuid form on the images of its compatibility
  list: from Fedora's own repositories, from EPEL on RHEL derivatives (enabled through the distribution's `epel-release`
  package with the EPEL key checked against a pinned fingerprint), from the project's PPA on Ubuntu (with the PPA key
  checked against a pinned fingerprint), and from the `.deb` of the newest GitHub release on Debian, which upstream
  publishes without checksum or signature, so that download relies on TLS alone.
- The feature declares `securityOpt` `seccomp=unconfined` and `apparmor=unconfined`, the settings without which an
  unprivileged process in a Docker container cannot create the user namespace Apptainer needs; it declares no
  `privileged`, `capAdd`, mount, entrypoint, or lifecycle command.
- Sandbox directories and `--unsquash` work without any device; mounting a SIF image needs `/dev/fuse`, which only the
  user's `runArgs` can add, and `--fakeroot` is unsupported. `NOTES.md` states this and the host requirements
  (unprivileged user namespaces; the AppArmor sysctl on Ubuntu 24.04 hosts).
- The feature has no options in this version: each source installs the version it currently ships.
- The feature can be installed twice.
- The repository's root `README.md` and `README.zh.md` list the feature.
- The `slurm` feature's use of Apptainer as its container backend is specified in the `slurm` change
  (`add-slurm-feature`), which orders `slurm` after this feature with `installsAfter` and never depends on it.

## Capabilities

### New Capabilities

- `apptainer`: installing Apptainer from the distribution, EPEL, the PPA, or the GitHub release; the security options
  the feature declares; what runs without privileges and what does not; repeated installation; failure behavior.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `apptainer`, new at version `1.0.0`. The `slurm` feature's ordering after it is part of the
  `slurm` change, not of this one.
- Files: `src/apptainer/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, generated `README.md`),
  `test/apptainer/` (`test.sh`, `duplicate.sh`, `scenarios.json` and its scripts, `compatibility.json`), and
  `openspec/specs/apptainer/spec.md` at archive; the root `README.md` and `README.zh.md` gain the feature's row.
- Security-sensitive surface for the package gate: `securityOpt` (two entries), the EPEL and PPA repositories with their
  pinned keys, and the unsigned GitHub `.deb` download on Debian.
- Dependencies: none (`dependsOn` and `installsAfter` empty).
- CI: the new feature's jobs on each compatibility image and architecture, plus one job per scenario; the scenarios pull
  a small image from Docker Hub.
- `test/canary.json` does not change.

## Acceptance

**Becomes true:**

- On every image of `test/apptainer/compatibility.json`, the scenarios of "Supported images", "Packages from the
  distribution", "Non-setuid installation", "Container security options", "Unprivileged execution", "Container
  metadata", and "Installing twice" pass in the feature's autogenerated, duplicate, or scenario tests: an unprivileged
  user builds a sandbox from a small Docker Hub image and runs a command in it.
- The scenarios of "EPEL on RHEL derivatives", "EPEL signing key", "PPA on Ubuntu", "PPA signing key", "GitHub release
  on Debian", and "Unsigned Debian download" pass in the autogenerated test on the images of their family, except "Key
  mismatch" of the two key requirements, "Unpinned release", "Release asset missing", "Digest reported", and "No digest
  reported", which are each verified by a manual run recorded in the PR's Validation section.
- "SIF without FUSE" and "SIF with FUSE" of "Unprivileged execution" are verified by manual runs, with and without
  `--device /dev/fuse`, recorded in the PR's Validation section, as are the AppArmor host checks of "Container security
  options" on an Ubuntu 24.04 Docker host.
- `src/apptainer/NOTES.md` states, for human readers: that the feature installs the non-setuid Apptainer and what that
  excludes (`--fakeroot`, setuid-only features); that the feature relaxes seccomp and AppArmor for the container and
  why; that the host must allow unprivileged user namespaces, with the sysctl Ubuntu 24.04 hosts need; that SIF images
  need `/dev/fuse` through the user's `runArgs` or `--unsquash`, while sandbox directories need nothing; where each
  distribution's package comes from, that the Debian package is an unsigned GitHub download, and that the installed
  version is what each source currently ships; and that the `slurm` feature uses Apptainer as its container backend when
  both are installed.
- `just check` passes, including `just validate` for the new feature's metadata, version `1.0.0`, and compatibility
  list, and `just docs` leaves the generated `src/apptainer/README.md` unchanged.
- The root `README.md` and `README.zh.md` each have one row for `apptainer`.
- `just test apptainer` and `just test-scenarios apptainer` pass locally.

**Stays true:**

- The feature requests no `privileged`, `capAdd`, `entrypoint`, `init`, `mounts`, `containerEnv`, or lifecycle command,
  and its `securityOpt` holds exactly the two entries the spec names.
- Every signing key the feature trusts is checked against a fingerprint the spec pins before it is used; no download
  weakens certificate, signature, or integrity checking.
- The setuid package is never installed, and no file installed by the feature is setuid.
- No other feature's files, version, or tests change.
