# Proposal

Implements [#57](https://github.com/hoshiori-dev/devcontainer-features/issues/57), part of the epic
[#127](https://github.com/hoshiori-dev/devcontainer-features/issues/127) (package-manager features: phase 2 controls).

## Why

After phase 1, `dnf-packages` installs only from the repositories the image enables and under the best-version policy
the image configures. A developer who needs one package from a repository the image ships disabled, such as CRB on a
RHEL 9 rebuild, has to write a Dockerfile; the same unpinned list upgrades an installed package on one image and leaves
it on another, with no way to say which is wanted; and download concurrency can only be changed by editing the image's
`dnf` configuration. The epic's bar is that a developer can choose among the sources and versions the image already
provides and tune downloads where the package manager supports it, while a feature with none of the new options set
behaves exactly as after phase 1.

## What Changes

- `dnf-packages` gains four options, each empty or `inherit` by default and each applying to one invocation only: a
  best-version policy (`best`), repositories of the image to enable (`enableRepositories`) or to leave out
  (`disableRepositories`) for the installation, and an upper bound of simultaneous downloads (`parallelDownloads`).
  Their contracts, interactions with the phase 1 options, and failure behavior are in `specs/dnf-packages/spec.md`.
- The feature states that it controls neither retries nor lock waiting, because `dnf` offers no bounded form of either
  on the supported generations, and that proxy settings and repository variables stay inherited. The issue's "bounded
  retries where supported" resolves to "not supported" (`design.md`, Decisions).
- The Purpose of `openspec/specs/dnf-packages/spec.md` is corrected by hand in this approval package: "the package
  repositories the image already configures and enables" becomes "the package repositories the image already
  configures", since a configured repository can now be enabled for an invocation. Its "Upstream sources" list is
  unchanged. OpenSpec ignores a delta's Purpose for an existing capability, so this edit travels beside the delta
  (`.agents/knowledge/spec-workflow.md`, Scope of specifications).
- Nothing changes when none of the new options is set: the phase 1 options keep their names, types, defaults, and
  values.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `dnf-packages`: best-version policy, per-invocation repository selection, a parallel-download bound, the validation of
  those controls, the scope of the signature requirement, and what a second installation keeps.

## Impact

- Feature ids touched: `dnf-packages` changes from `1.0.1` to `1.1.0` (MINOR: new options, backward-compatible
  behavior). No other feature changes and none depends on it.
- Implementation after approval: `src/dnf-packages/` (`install.sh`, `devcontainer-feature.json`, `NOTES.md`, and
  `README.md` generated by `just docs`) and `test/dnf-packages/` (scenarios and `duplicate.sh`). No compatibility image,
  script, workflow, knowledge file, or dev container configuration changes.
- This commit carries planning only: the delta spec, the design, and the Purpose correction. The metadata version and
  the implementation follow together after the package gate closes; the published artifact is not claimed to implement
  the new controls.
- Out of scope, unchanged from the issue: creating repositories, importing keys, erasing installed packages, changing
  how pins and downgrades behave (phase 3, [#62](https://github.com/hoshiori-dev/devcontainer-features/issues/62)),
  offline installation, release-version or architecture overrides, and arbitrary `dnf` settings.

## Acceptance

**Becomes true:**

- Every scenario of the requirements this delta adds ("Option best", "Option enableRepositories", "Option
  disableRepositories", "Option parallelDownloads", "Best-version policy is scoped to installation", "Repository
  selection is scoped to installation", "Parallel downloads are bounded", "Undeclared settings are inherited") passes on
  each supported `dnf` generation, with the test, image, architecture, and result recorded in the PR's Validation
  section.
- The scenarios this delta adds to the modified requirements pass the same way: "Parallel download boundaries are
  validated", "Best policy values are validated", "Repository identifiers are validated", "Spaces and empty items in a
  repository list are ignored", "Identifier in both repository lists is refused", "Temporarily enabled repository keeps
  its own checks", "Repository selection leaves the configuration unchanged", "Repository selection does not carry
  over", and "Same repository and solver controls on the second install".
- `src/dnf-packages/devcontainer-feature.json` has version `1.1.0` and declares exactly the options of the spec as
  archive would produce it; `NOTES.md` and the generated README describe each new option, and state what stays inherited
  and that retries and lock waiting have no option.
- The Purpose of `openspec/specs/dnf-packages/spec.md` reads as corrected in this package.
- `just check`, `just test dnf-packages`, and `just test-scenarios dnf-packages` pass.

**Stays true:**

- With `best`, `enableRepositories`, `disableRepositories`, and `parallelDownloads` omitted, the feature behaves as
  version `1.0.1` does: every existing scenario of `openspec/specs/dnf-packages/spec.md` keeps its name and still
  passes, including "Invalid control fails before any change", "Empty list ignores installation controls", and "Timeout
  boundaries are validated".
- `packages`, `installWeakDeps`, `refreshPolicy`, `cleanup`, and `networkTimeout` keep their names, types, defaults, and
  `enum` values.
- The feature adds no repository and no key, changes no repository file, key file, or `dnf` configuration file, and
  relaxes no signature or TLS check: the scenarios under "Package signature checking stays in effect".
- An invalid option fails with status 1 before any package-manager call, also with an empty package list, and an empty
  list with valid options stays a no-op on an image without `dnf`.
- No option passes arbitrary arguments, settings, environment variables, a proxy, or a configuration file path to `dnf`.
- Installed packages are not erased to resolve a conflict, and a pinned version is installed as before: "Installed
  packages are not erased" and "Version and architecture qualifiers" are untouched.
- The compatibility images and architectures stay as they are; `devcontainer-feature.json` declares none of
  `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`, `containerEnv`, lifecycle commands,
  `dependsOn`, or `installsAfter`.
- Only `src/dnf-packages/`, `test/dnf-packages/`, and `openspec/` change.
