# Proposal

Implements [#197](https://github.com/hoshiori-dev/devcontainer-features/issues/197).

## Why

Lean 4 is a widely used language and proof assistant for formal mathematics and verification, and its official setup
goes through elan, the Lean version manager. Developers and coding agents who want to write proofs in a dev container
have no feature in the collection for it. Upstream's documented route pipes an installer script into a shell, always
installs the newest elan, and edits shell profiles. It also keeps every toolchain under the user's home directory, so
the toolchains are lost with the container. A toolchain is about 570 MB to download and about 3.1 GB unpacked, and
projects that follow Mathlib move to a new toolchain about once a month.

## What Changes

- A new feature `lean` installs elan from its GitHub release archives as `/usr/local/bin/elan`. It also adds the `lean`,
  `lake`, and other proxies elan's own installer creates, so they are on `PATH` for every user. Each project's
  `lean-toolchain` file keeps selecting its own Lean version, which elan installs on first use.
- Option `elanVersion` chooses the elan release: `latest`, or a release from `4.1.0` on.
- Option `defaultToolchain` sets the toolchain elan uses outside a project. It is set again each time the dev container
  is created; an empty value leaves elan's default to the user.
- Option `preinstallToolchains` installs the listed toolchains into the image at build time, so they run without a
  download. Toolchain names in both options are limited to upstream's official release channels, versions, and
  nightlies.
- elan's home, holding the toolchains installed at run time, and Lake's and Mathlib's caches, live on a named volume for
  each dev container. They therefore survive rebuilds. When the container is created, the feature prepares the volume
  for the remote user and links the image's build-time toolchains into elan's home. It also repairs the volume's
  ownership when it no longer fits the remote user.
- The feature requests the VS Code extension `leanprover.lean4`.
- The feature installs the download prerequisites, git included, which Lake needs to fetch dependencies.
- The feature is installable twice on the same image, with the same or different options.
- `test/lean/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `lean`: installing elan and its proxies, choosing the elan release, setting elan's default toolchain, installing
  toolchains at build time, keeping elan's home and the Lake and Mathlib caches on a per-container volume and preparing
  it when the container is created, the editor extension, installing twice, and failing on unsupported platforms or
  invalid options.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `lean`, new at version `1.0.0`.
- Files: `src/lean/` (`devcontainer-feature.json`, `install.sh`, the container-creation script under `scripts/`,
  `NOTES.md`, and `README.md` generated by `just docs`); `test/lean/` (`test.sh`, `duplicate.sh`, scenarios and their
  files, `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated
  row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: `containerEnv` (`ELAN_HOME`, `LAKE_CACHE_DIR`, `MATHLIB_CACHE_DIR`), one named volume in `mounts`,
  `onCreateCommand`, `installsAfter` for `common-utils`, and the VS Code extension. There is no `dependsOn`,
  `privileged`, `capAdd`, `securityOpt`, `init`, or `entrypoint`.
- Network at build time: GitHub for the elan release, and, only when `preinstallToolchains` is not empty, the Lean
  release index and toolchain hosts (design.md, URL inventory). The image's configured package repositories supply
  missing prerequisites. When the container is created, the feature itself makes no network request.
- Image size: each toolchain in `preinstallToolchains` adds about 3.1 GB to the image; with the default, none is added.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes. The install-twice test installs one
  toolchain on every image, about 570 MB downloaded per job.
- Security: upstream publishes no checksum or signature for elan releases or Lean toolchains, and elan verifies none
  when it downloads a toolchain. The delta spec states both risks. Toolchains are executable code on a volume, so the
  volume is per dev container.

## Acceptance

**Becomes true:**

- Every scenario in `specs/lean/spec.md` that a successful container build or a scenario script can show holds on every
  image and architecture in `test/lean/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios.
  Every other scenario holds in the check design.md (Tests) names for it, run once. Each result is recorded in the PR's
  Validation section.
- `test/lean/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/lean/devcontainer-feature.json` has version `1.0.0`, and `src/lean/README.md` and the root `README.md` are what
  `just docs` generates.
- `src/lean/NOTES.md` covers the topics the spec's "Lean usage guidance" requirement names.
- `README.zh.md` holds the translated row for `lean` in its feature list.
- `just test lean` and `just test-scenarios lean` pass locally, and the PR's container test jobs pass on amd64 and
  arm64.

**Stays true:**

- The feature runs no project command (`lake build`, `lake exe cache get`, `lake update`) and installs no Lean package
  or Mathlib.
- The feature never sets `ELAN_TOOLCHAIN`, so each project's `lean-toolchain` keeps deciding its toolchain.
- The feature declares no `dependsOn`, `privileged`, `capAdd`, `securityOpt`, `init`, or `entrypoint`.
- No file outside `src/lean/`, `test/lean/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
