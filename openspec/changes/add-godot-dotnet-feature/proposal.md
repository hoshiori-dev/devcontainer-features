# Proposal

Implements [#192](https://github.com/hoshiori-dev/devcontainer-features/issues/192).

## Why

Godot projects written in C# need the .NET build of the Godot editor, together with a .NET SDK, to build their scripts,
run, import, and export; the standard build cannot load C# scripts at all. The collection's `godot` feature installs
only the standard build, so a dev container for a C# Godot project still falls back on an unverified download in a
Dockerfile or a community image.

## What Changes

- A new feature `godot-dotnet` installs the .NET build of the Godot editor from upstream's verified GitHub release
  archives as `godot`, on `PATH` for every user of the container, at the stable release its `version` option names or
  the latest stable release.
- The feature brings in a .NET SDK through the first-party feature `ghcr.io/devcontainers/features/dotnet` at its
  long-term-support release, so `godot --headless` builds and runs a C# project's scripts, runs projects, and serves the
  GDScript language server in the container. The first build of a C# project needs network access to nuget.org.
- `godot-dotnet` and `godot` are mutually exclusive: both provide the `godot` command, and whichever of the two is
  installed second fails the build instead of replacing the other.
- The feature supports only the distributions the dotnet feature supports (Debian and Ubuntu), and installs what the
  official build needs to run without a display and nothing for a graphical session.
- The feature declares no editor customizations of its own. Its `NOTES.md` says what the dotnet dependency brings into
  the container and the editor (the SDK, its environment, shell completions, packages, and the C# extension), shows how
  a user adds the Godot Tools extension in their own configuration, as the `godot` feature does, and says that export
  templates and pre-releases are not covered.
- The feature is installable twice on the same image, with the same or different options.
- `test/godot-dotnet/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `godot-dotnet`: installing the .NET build of the Godot editor for headless use with a .NET SDK, choosing its stable
  release, verifying the download, checking that the installed build runs, staying exclusive with the `godot` feature,
  installing twice, and failing on unsupported platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `godot-dotnet`, new at version `1.0.0`. The `godot` feature is not changed: its requirement that
  `/usr/local/bin/godot` be absent or a regular file, approved on #189, already makes it fail after `godot-dotnet`. This
  pull request merges after #189.
- Files: `src/godot-dotnet/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/godot-dotnet/` (`test.sh`, `duplicate.sh`, `scenarios.json` with its scenario scripts and the
  helpers its failure scenario uses, `compatibility.json`); the root `README.md` (its generated feature list) and
  `README.zh.md` (the translated row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: `dependsOn` `ghcr.io/devcontainers/features/dotnet:2` with options `{"version": "lts"}`; no
  `customizations`, `installsAfter`, `containerEnv`, `privileged`, `capAdd`, `securityOpt`, `mounts`, `init`,
  `entrypoint`, or lifecycle command of its own.
- Network at build time: `github.com` and the host GitHub's release downloads redirect to (design.md, URL inventory),
  the image's configured package repositories when a prerequisite is missing, and what the dotnet feature fetches for
  the SDK; nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes. Each install downloads one Godot
  archive of about 110 MB and, through the dependency, one .NET SDK of about 230 MB.
- Security: upstream publishes a SHA-512 checksum file and no signature, so the archive is verified against the checksum
  file, which relies on TLS alone; the dotnet feature downloads the SDK with Microsoft's install script, which checks
  only the file size. The delta spec states both.

## Acceptance

**Becomes true:**

- Every scenario in `specs/godot-dotnet/spec.md` that a successful container build can show holds on every image and
  architecture in `test/godot-dotnet/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios;
  every other scenario holds in the check design.md (Goals) names for it, run once. Each result is recorded in the PR's
  Validation section.
- `test/godot-dotnet/compatibility.json` lists exactly the images and architectures planned in design.md (Supported
  images).
- `src/godot-dotnet/devcontainer-feature.json` has version `1.0.0`, and `src/godot-dotnet/README.md` and the root
  `README.md` are what `just docs` generates.
- `src/godot-dotnet/NOTES.md` states that the feature is for headless use and installs nothing for a graphical session;
  that it cannot be combined with the `godot` feature; what the dotnet dependency adds (the long-term-support .NET SDK,
  its environment variables and `PATH` entries, shell completions and packages, and in VS Code the C# extension, with
  what that extension runs in a C# workspace and how to opt out of it, and a Copilot instruction setting); how a project
  adds another SDK, and that a newer .NET major beside it becomes the one the editor builds with and may break the
  editor's C# builds; that a C# project's first build fetches packages from nuget.org; shows how to add the Godot Tools
  extension and turn on its headless language server in the user's own `customizations`, with the same statement of what
  the extension runs that the `godot` feature's `NOTES.md` makes; tells users to pin `version` to their project's
  release; shows how to install the .NET export templates for the installed version from the same GitHub release,
  verified against its `SHA512-SUMS.txt`, and where Godot looks for them; and says that pre-releases are not covered.
- `README.zh.md` holds the translated row for `godot-dotnet` in its feature list.
- `just test godot-dotnet` and `just test-scenarios godot-dotnet` pass locally, and the PR's container test jobs pass on
  amd64 and arm64.

**Stays true:**

- The feature has no option that takes a credential, a token, a URL, or a path.
- The feature declares no `customizations`, `installsAfter`, `mounts`, `capAdd`, `privileged`, `securityOpt`, `init`,
  `entrypoint`, or lifecycle command, and no `dependsOn` other than the dotnet feature.
- No file outside `src/godot-dotnet/`, `test/godot-dotnet/`, the root `README.md`, `README.zh.md`, and this change
  changes.
- `just check` passes, and every required check passes on this PR.
