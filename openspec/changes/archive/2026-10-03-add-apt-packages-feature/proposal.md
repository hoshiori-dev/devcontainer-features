# Proposal

Implements [#20](https://github.com/hoshiori-dev/devcontainer-features/issues/20).

## Why

A dev container on Debian or Ubuntu that needs a few extra system packages today needs a Dockerfile, or a broader
feature that also adds repositories and configures the system. The collection has no feature that only installs a list
of packages with `apt`. `apt-packages` is the first of five atomic installers, one per package manager (`apt-packages`,
`dnf-packages`, `apk-packages`, `pacman-packages`, `zypper-packages`), which share one option shape and one set of
guarantees.

## What Changes

- A new feature `apt-packages` installs the system packages named in one option with `apt-get`, from the repositories
  the image already configures, and nothing else: no repositories, keys, or apt configuration of its own. Its contract
  is `specs/apt-packages/spec.md`.
- The repository's root `README.md` lists the feature: one row under "## Features" whose id links to `src/apt-packages/`
  and gives a one-sentence description; if it is the first row, it replaces "No features have been published yet."

## Capabilities

### New Capabilities

- `apt-packages`: installing a list of system packages with `apt-get` from the image's configured repositories.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `apt-packages`, new, first published at version `1.0.0`. No other feature changes, and none
  depends on it, so CI tests only `apt-packages`.
- Files: `src/apt-packages/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/apt-packages/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` with its
  scenario scripts, and the direct checks named in `design.md`, Test plan); `openspec/specs/apt-packages/spec.md`,
  created when the change is archived.
- Supported images: the planned compatibility list is in `design.md` (Supported images); `test/apt-packages/`
  `compatibility.json` becomes its source of truth.
- `README.md` at the repository root: the "## Features" row for `apt-packages` (What Changes).
- Canary membership in `test/canary.json` is left to the maintainer; this change does not touch the file.
- No script, workflow, test infrastructure, or knowledge file changes.

## Acceptance

The maintainer approved the review corrections in conversation on 2026-10-04: installations may not remove existing
packages; conflicting lists fail without changing installed packages; exact actual and virtual names and pinned versions
are checked before installation, including trailing `+`. The first release remains `1.0.0`.

**Becomes true:**

- Every scenario in `specs/apt-packages/spec.md` passes in the test named for it in `design.md` (Test plan), and the
  PR's Validation section names each scenario with its test, image, architecture, and result:
  - scenario tests (`just test-scenarios apt-packages`) run in CI on amd64, each on the image its `scenarios.json` entry
    names;
  - the autogenerated and install-twice tests (`just test apt-packages`) run in CI on every image and architecture in
    `test/apt-packages/compatibility.json`;
  - the direct checks under `test/apt-packages/` run locally on every amd64 image in that list, and their output is
    recorded in the Validation section; CI does not run them.
- The issue's acceptance sketch is covered by the scenarios "Listed packages are installed", "Image without apt-get
  fails clearly", and "Different list on the second install".
- `test/apt-packages/compatibility.json` lists exactly the images and architectures planned in `design.md`.
- `src/apt-packages/devcontainer-feature.json` has version `1.0.0` and a single option, `packages`; `just check` passes,
  including the README generated by `just docs`.
- The root `README.md` has, under "## Features", a row for `apt-packages` whose id links to `src/apt-packages/` and
  whose description is one sentence, and it no longer says "No features have been published yet."; this row is separate
  from the generated `src/apt-packages/README.md`.

**Stays true:**

- The feature fetches nothing itself: `install.sh` contains no URL and no download tool, and every package comes from
  the repositories configured in the image.
- The feature never disables or weakens signature checking and itself adds, removes, or edits no repository, key, or apt
  configuration file (scenarios under "Repository authentication stays in effect").
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, or lifecycle commands.
- No file outside `src/apt-packages/`, `test/apt-packages/`, `openspec/`, and the root `README.md` changes; every
  required check passes on the PR.
