# Design

## Context

- `scripts/test_feature.ts` stages a copy of `src/` and `test/` in a temporary directory, rewrites the in-repo
  references in it (`scripts/lib/stage.ts`), publishes the staged features to a throwaway registry, and runs
  `devcontainer features test` on the copy. CI and `just test*` both go through it.
- The CLI copies a feature's whole test folder into the container and runs the scenario script from there as the
  scenario's `remoteUser`. Existing tests rely on it: they source `test/<id>/checks.sh` or `helpers.sh`.
- The harness limits the issue names: a failing `install.sh` fails the image build, so no script runs; a `build`
  scenario's context cannot reach `src/`; the install-twice test's second run uses the default options.
- What the eight runners do, read on 2026-10-07: each starts a container from a compatibility image with `src/<id>`
  mounted read-only, runs `install.sh` through `docker exec` with chosen environment variables, and asserts the exit
  status, the output, and the package manager's state. Beyond that they use three host-side operations: starting the
  container without a network, disconnecting it from the network after a preparation step, and (`control_checks.ts`)
  listening on a host port that the container reaches through the host network.
- Measured on 2026-10-07 with the devcontainer CLI 0.89.0, on a throwaway copy of this checkout in which
  `src/apt-packages` had been copied to `test/apt-packages/_feature` and three scenarios installed `apt-packages`
  without options:
  - On `debian:12` (root) the script found `./_feature/install.sh` executable in its working directory. Running it with
    a path and with a command substitution as an entry exited 1 with the refusal message, installed nothing, and created
    no file; a further run with `PACKAGES=bc` installed `bc`.
  - On `mcr.microsoft.com/devcontainers/base:ubuntu24.04` with `remoteUser: vscode` the same checks passed through
    `sudo env … ./_feature/install.sh`.
  - A scenario with `"runArgs": ["--network=none"]` built with a network and ran its script without one: name resolution
    failed, and `install.sh` exited 1 at the index refresh without installing.
- Measured the same day on a second throwaway copy in which all 114 scenarios of the repository had been renamed to
  `test_<name>` — key, script, and folder of extra files — and one `fail_*` scenario added: `scripts/validate.ts`
  reported every feature as valid, shellcheck and the unit tests of `scripts/` passed, and a plain scenario, a `fail_*`
  scenario, a `build` scenario with its folder, a global scenario, and `test.sh` with `duplicate.sh` beside the
  `test_*.sh` files all passed in containers. No script under `scripts/` reads a scenario's name, and no test script
  refers to another scenario's file; the old names appear only in comments.
- Not measured, and assumed by this design:
  1. The test folder reaches the container the same way for a `build` scenario and on the arm64 runners.
  2. Every compatibility image of the five installers either runs its scenarios as root or offers `sudo` without a
     password to its `remoteUser`.
  3. A server a script starts inside its container on a loopback address can stand in for the host-side listener of
     `control_checks.ts`.
  4. An image prepared by a scenario's Dockerfile, run without a network, can stand in for disconnecting a container
     after a preparation step.

## Goals / Non-Goals

**Goals:**

- The installer a script runs is byte-identical to `src/<id>/` of the checkout. Checked by a unit test of the staging
  function that compares the two trees.
- Staging is the only place the copy exists. Checked by `just validate` rejecting the reserved name in the repository,
  and by the unit test that covers the rejection.
- What the CLI installs is unchanged by the copy: the staged `src/`, the published set, and the rewritten references are
  the same with and without it. Checked by the existing staging tests passing unchanged.
- A script's own run of the installer has the privileges of the test container and no more. Checked by reading the
  scenarios added: none sets a property from the list in the proposal's Stays true.
- A check that fails names the entry or the list it ran with and shows the installer's output. Checked by reading a
  failing run produced for the proposal's working-tree observation.

**Non-Goals:**

- Asserting a failure of the image build itself. A run of the installer from a script does not pass through the CLI's
  wrapper, so the conversion of option names to environment variables and the `_REMOTE_USER` variables are what the
  script sets, as in the runners today. The autogenerated and scenario tests keep covering the wrapper for successful
  installs.
- A declaration format for expected failures. The scenario script is the declaration.
- A shared shell library for the new checks. Each feature keeps its helpers in its own test folder, as today; a shared
  one would need its own staging rule and a rule in `shell-style.md`, and is left until two features repeat more than
  the few lines that run the installer.
- Moving the runners of `hf-cli` and `colab-cli`.

## Decisions

- **The failure happens in the test, not in the build.** A scenario installs the feature through the CLI with options
  under which it succeeds — for the five installers, an empty list, which installs nothing — and the script then runs
  the installer itself. The container exists, so the status, the output, and the state are all open to assertion, and
  one script can run many entries in one container. Rejected:
  - A JSON file declaring scenarios that are expected to fail, whose build log is handed to a checking script. After a
    failed build there is no image, so "nothing was installed" and "the command in the entry did not run" cannot be
    asserted, and those are what a refusal check is for. The log also prints the option values, so finding the refused
    entry in it proves nothing; the build fails for unrelated reasons such as a failed pull; and each entry costs one
    image build.
  - One shared host-side runner in `scripts/` driven by a JSON declaration. It keeps a second test pipeline beside the
    CLI's, needs its own CI job and its own selection rule, and the checks that choose a package or a version at run
    time do not fit a static declaration.
- **Staging copies the feature's sources into its test folder.** For every staged feature that has a test folder,
  `src/<id>/` is copied whole to `test/<id>/_feature/` in the staging directory, from the checkout and before any
  reference is rewritten, so the copy is the source and not its staged variant. The whole directory, not `install.sh`
  alone: `firewall` and `uv` ship further files beside it. Rejected:
  - A symbolic link committed in `test/<id>/`. It must survive two copies it does not control — the staging copy and the
    CLI's — and a link kept as a link dangles in a container that has no `src/`. It is also listed twice by
    `git ls-files '*.sh'`, which feeds shellcheck, and is unreliable on a Windows checkout.
  - A committed copy. It drifts from `src/`.
  - Copying into a `build` scenario's context. It reaches only `build` scenarios and puts the installer's run into the
    build again.
- **The name `_feature` is reserved.** `just validate` rejects a tracked path `test/<id>/_feature` and a scenario named
  `_feature`, whose folder of extra files would be that path. The leading underscore follows `test/_global`.
- **A script runs the installer as root through `sudo` when it is not root.** No scenario changes its `remoteUser` for
  the purpose, so the checks run on the images as they are listed.
- **No network is a scenario property.** A check that needs an offline container sets `runArgs` to `--network=none` in
  its scenario. A check that needs a prepared image and then no network prepares the image in the scenario's Dockerfile.
  An image outside the compatibility list — the one without the package manager — is a `build` scenario, which the image
  rule of `testing.md` already exempts.
- **The prefix names the subject, not the outcome.** A `fail_*` scenario passes like any other: what fails is a run of
  the installer inside its script. A script often holds both kinds of assertion — a refusal, then a list that installs —
  so the prefix follows what the scenario exists to show: `fail_` when that is an installation that must fail, `test_`
  otherwise. `test.sh` and `duplicate.sh` keep their names, which the CLI fixes. Rejected:
  - Renaming every feature's scenarios here. It changes `test/` of nine features this change has no other reason to
    touch, and CI then runs the whole collection's matrix for a rename.
  - Enforcing the prefixes in `just validate` now. The rule would be false for nine features until they are renamed, so
    enforcement goes with their renaming.
  - Naming only the new scenarios and leaving the installers' existing ones. Each of the five folders would then hold
    two conventions.
- **A check that does not fit is not dropped.** If a runner's check cannot be written as a scenario — one of the four
  assumptions under Context fails for it, or it needs something no scenario offers — the work on that feature stops, the
  check is listed in the pull request with what it needs, and a maintainer decides whether it stays as a manual check,
  is rewritten, or is given up. The runner file stays until then.
- **One pull request, one feature at a time.** The mechanism lands first with `apt-packages`, whose scenario job then
  proves it in CI; the other four follow on the same branch. Each runner is deleted in the commit that completes its
  feature's scenarios.

## Risks / Trade-offs

- **Scenario jobs take longer.** Every new scenario is one image build and one container. Mitigation: checks that share
  a preparation share a scenario, as the runners' refusal checks already share a container; the scenario count and the
  job durations before and after are recorded in the Validation section.
- **Checks that read live repositories fail for upstream reasons.** A mirror outage or a package dropped from an archive
  turns a scenario job red on an unrelated pull request. The runners have the same exposure but were run by hand.
  Mitigation: the checks that choose a package or version at run time keep doing so; a check found flaky in CI is
  reported to a maintainer and not weakened or retried into passing (`agent-authority.md`, Escalation).
- **The copy is visible to every test of the feature.** `test.sh` and `duplicate.sh` find `_feature/` beside them too.
  Nothing reads it unless a script chooses to, and the reserved name keeps it from colliding with a scenario.
- **A script can run the installer with root rights.** It could before: the test container is disposable, the installer
  is the code under review, and the runners did the same through `docker exec`. Review of test scripts follows
  `review-guidance.md` as today.
- **The staged copy carries the unrewritten metadata.** `_feature/devcontainer-feature.json` names GHCR, not the local
  registry. A script that runs `install.sh` does not read it; `testing.md` says the copy is for running the installer
  and not for resolving references.

- **Two naming conventions exist until the follow-up lands.** Five features follow the rule and nine do not, and nothing
  checks it. `testing.md` says so and names the issue; a scenario added to one of the nine in the meantime follows the
  rule only if its author reads that.

## Migration Plan

Merging is the deployment. The new scenarios run for a feature from the first pull request that affects it. Rollback is
a revert: the runners return with it, and the staged copy disappears.
