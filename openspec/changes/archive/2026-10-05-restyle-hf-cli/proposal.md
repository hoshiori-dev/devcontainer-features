# Proposal

Implements [#77](https://github.com/hoshiori-dev/devcontainer-features/issues/77), part of
[#52](https://github.com/hoshiori-dev/devcontainer-features/issues/52).

## Why

The hf-cli scripts predate `.agents/knowledge/shell-style.md`: `install.sh` runs its logic at top level with four-space
indentation, uses indirect expansion and two message prefixes that do not match the guide, logs neither its apt nor its
network steps before they run, and checks the `uv` precondition only after apt has already changed the image. The #52
audit also confirmed unclear download failures, a split installer URL, a repeated endpoint URL, a silent recovery path
without a stated reason, and a thin script header. Developers who audit the feature or read its build log should find
each step, each source, and each failure stated plainly.

## What Changes

- `src/hf-cli/install.sh` follows the shell style guide: a header naming what is installed, from where, to which paths,
  and the options' environment variables; constants for every URL, version floor, and path the feature creates or
  modifies; named steps called from `main`; no indirect expansion.
- Every log line starts with `hf-cli:` and every failure with `hf-cli: error:`, in lower case and without a trailing
  period. Each failure the developer can fix names the value at fault and how to fix it, and keeps every name the spec's
  scenarios require.
- The build log has one line before each step that changes the image or uses the network: the apt installation, the
  latest-version request, the installer download, the installer run, the skill generation, and the system link.
- A download failure names its URL and a cause that carries no proxy value (HTTP status, refused redirect, or error
  class); a local write error surfaces with Python's own message, ahead of the call site's failure line.
- The `uv` version check runs before anything changes in the image; an unreadable `/etc/os-release` fails with a message
  saying so.
- The test scripts under `test/hf-cli/` and the global scenario script `test/_global/uv_and_hf_cli.sh` follow the guide:
  strict shell options, labels in the spec's words, a comment above each expected value computed at run time, and named
  helpers for multi-line assertions. The hand-run Deno runners match the new messages and name all three image arguments
  they need.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. No requirement or scenario of `hf-cli` changes; the change sets `skip_specs: true`.

## Impact

- Feature id touched: `hf-cli`, version `1.0.0` to `1.0.1` (PATCH). Every change under `src/hf-cli/` needs a bump, and
  this one changes only fixes, log and failure text, and the order of a precondition check, with identical install
  results (`.agents/knowledge/feature-authoring.md`, Versions).
- Files touched after approval: `src/hf-cli/install.sh`, `src/hf-cli/devcontainer-feature.json` (version only),
  `src/hf-cli/README.md` regenerated by `just docs`; `test/hf-cli/test.sh`, `duplicate.sh`, and the seven scenario
  scripts; `test/hf-cli/direct_checks.ts` and `integration_checks.ts` (expected substrings and argument messages);
  `test/_global/uv_and_hf_cli.sh`, the global scenario script that installs `uv` and `hf-cli` together, which this
  change owns.
- Not touched: options, `installsAfter`, `containerEnv`, `NOTES.md`, `scenarios.json`, `compatibility.json`, the
  scenario Dockerfiles, `hash_checks.ts`, `test/_global/scenarios.json`, the `uv` feature, and anything outside
  `src/hf-cli/`, `test/hf-cli/`, `test/_global/uv_and_hf_cli.sh`, and this change.

## Acceptance

**Becomes true:**

- `shellcheck -o require-variable-braces,require-double-brackets` reports nothing for `src/hf-cli/install.sh`, every
  `*.sh` under `test/hf-cli/`, and `test/_global/uv_and_hf_cli.sh`.
- `src/hf-cli/install.sh` ends with `main "$@"`, has no executable code between its function definitions, and contains
  no `eval`, indirect expansion, or `set -x`.
- Every line the feature itself writes to the build log starts with `hf-cli:`, and every failure line with
  `hf-cli: error:`; none starts with an upper-case letter or ends with a period.
- A build log of a default install shows, before each happens, the apt installation (when packages are missing), the
  request to the latest-version endpoint, the installer download with its URL, the installer run with its user and
  target directory, and the link `/usr/local/bin/hf`; a skill-only reinstall shows the skill generation.
- With a `uv` older than `0.12.16` on the system `PATH` of an image that lacks `python3`, the build fails naming both uv
  versions and `apt-get` never runs.
- A missing release tag fails with messages naming the tag's installer URL and the HTTP status; an unreachable
  latest-version endpoint fails with a message naming the endpoint.
- `src/hf-cli/devcontainer-feature.json` has version `1.0.1`, and `src/hf-cli/README.md` equals `just docs` output.
- `test/hf-cli/direct_checks.ts` and `test/hf-cli/integration_checks.ts` pass against images built from the restyled
  feature.
- `just check`, `just test hf-cli`, `just test-scenarios hf-cli`, and `just test-global` pass.

**Stays true:**

- Download sources, TLS verification, the refusal of redirects, package digest verification, and the absence of any
  checksum or signature the feature would compare are unchanged; the feature requests no URL it did not request before.
- Every Requirement and Scenario in `openspec/specs/hf-cli/spec.md` still holds.
- What an install leaves in the image (the virtual environment and its packages, `/usr/local/bin/hf`, the skill files)
  is the same for every option combination, and every `check` of the test scripts under `test/hf-cli/` and of
  `test/_global/uv_and_hf_cli.sh` still passes.
- The feature still installs twice, with the same and with different options, as Requirement "Install twice" states.
- Options, their defaults, and their accepted values are unchanged; an explicitly empty `version` or `installSkill`
  still fails.
- No message of the feature prints a proxy variable's value or an exception's text; `HF_HUB_OFFLINE=1` stays out of the
  container environment.
- Supported images and architectures are unchanged.
