# Proposal

Implements [#181](https://github.com/hoshiori-dev/devcontainer-features/issues/181).

## Why

A developer who changes a repository's GitHub Actions workflows today learns whether they work only after pushing. act
runs those workflows locally against a Docker Engine, so the feedback loop stays inside the dev container. The
collection has no feature that installs it, and act's first run asks interactively for a default runner image, which
aborts wherever no terminal is attached, such as an agent or a lifecycle command.

## What Changes

- A new feature `act` installs the `act` executable from upstream's verified GitHub release archives, on `PATH` for
  every user of the container, at the release its `version` option names or the latest release.
- Its `defaultImage` option, when set to anything but `none`, writes the remote user's act configuration file with the
  runner images act's own first-run prompt writes for that choice, so act never prompts; by default it writes nothing.
- The container environment disables act's per-run request for upstream's version notices.
- The feature installs no container engine and depends on no Docker feature; it is ordered after the Docker features of
  `devcontainers/features`, and its `NOTES.md`, and so its generated README, explains how to give act a Docker Engine
  and why the feature does not install one.
- The feature is installable twice on the same image, with the same or different options.
- `test/act/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `act`: installing the act runner for GitHub Actions workflows, choosing its version, verifying the download,
  preselecting its default runner images, disabling its version notices, installing twice, and failing on unsupported
  platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `act`, new at version `1.0.0`.
- Files: `src/act/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by `just docs`);
  `test/act/` (`test.sh`, `duplicate.sh`, `checks.sh`, `scenarios.json` with its scenario scripts,
  `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: `containerEnv` sets `ACT_DISABLE_VERSION_CHECK`; `installsAfter` names
  `ghcr.io/devcontainers/features/docker-in-docker` and `ghcr.io/devcontainers/features/docker-outside-of-docker`. No
  `dependsOn`, `privileged`, `capAdd`, `securityOpt`, `mounts`, `init`, `entrypoint`, or lifecycle command.
- Network at build time: `github.com` and the host GitHub's release downloads redirect to (design.md, URL inventory),
  plus the image's configured package repositories when a prerequisite is missing; nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes.
- Security: upstream publishes a checksum file and no signature, so the archive is verified against the checksum file,
  which relies on TLS alone; the delta spec states it.

## Acceptance

**Becomes true:**

- Every scenario in `specs/act/spec.md` that a successful container build can show holds on every image and architecture
  in `test/act/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios; every other scenario
  holds in the check design.md (Goals) names for it, run once. Each result is recorded in the PR's Validation section.
- `test/act/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/act/devcontainer-feature.json` has version `1.0.0`, and `src/act/README.md` and the root `README.md` are what
  `just docs` generates.
- `src/act/NOTES.md` states that act needs a Docker Engine the feature does not install, shows how to add one with
  docker-in-docker or docker-outside-of-docker, says why the feature does not depend on either, and explains
  `defaultImage` and the first-run prompt it avoids.
- `README.zh.md` holds the translated row for `act` in its feature list.
- `just test act` and `just test-scenarios act` pass locally, and the PR's container test jobs pass on amd64 and arm64.

**Stays true:**

- The feature has no option that takes a credential, token, secret, or event payload, and runs no workflow at build
  time.
- The feature declares no `dependsOn`, `mounts`, `capAdd`, `privileged`, `securityOpt`, `init`, `entrypoint`, or
  lifecycle command.
- No file outside `src/act/`, `test/act/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
