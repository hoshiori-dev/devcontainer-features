# Design

## Context

See [proposal.md](proposal.md) for motivation and acceptance.

`buildPlan` currently returns scenario entries containing only `feature`. The workflow runs those entries on
`ubuntu-24.04`, then separately runs glab scenarios on `ubuntu-24.04-arm`. `RUNNERS` already maps both supported
architectures to native runners. `scenarioImages` and `scenarioImageProblems` use the fixed `SCENARIO_ARCH` of amd64.

Glab's eight version scenarios use four images already declared for both architectures. Its archived change explicitly
requested native arm64 scenario coverage. Compatibility loading validates against `test/compatibility.schema.json`;
version checks compare supported image/architecture pairs rather than every field in the test configuration.

## Goals / Non-Goals

**Goals:**

- Keep architecture defaults and runner selection in the repository model shared by planning and validation; verify
  default and explicit declarations in unit tests.
- Make scenario architecture expansion independent of feature names; verify the plan for generic test fixtures as well
  as the glab configuration.
- Validate the full set of scenarios for each selected architecture. A feature/architecture job runs the entire scenario
  file, so partial image support must fail validation rather than silently reduce coverage.

**Non-Goals:**

- No per-scenario architecture filters or cross-architecture emulation. Local `just test-scenarios` continues to run on
  the host architecture; its CLI and execution script remain unchanged, verified by the diff.
- No change to global scenario architecture or feature compatibility pairs; verify their existing validation tests and
  compare the test plan before and after implementation.

## Decisions

### Declare scenario architectures in the compatibility list

Add optional top-level `scenarioArchitectures` to `test/<id>/compatibility.json`. Its schema accepts a nonempty, unique
array containing `amd64` and/or `arm64`; omission means `["amd64"]`. A shared accessor provides that default to planning
and validation. Glab declares `["amd64", "arm64"]`; other compatibility files remain untouched.

This field selects CI scenario coverage. `images[].arch` remains the declaration of supported image/architecture pairs
and the source for autogenerated and duplicate tests. Changing only the new field does not change supported platforms or
require a feature version bump.

Inferring scenario architectures from the union of image architectures would expand other features' coverage and could
schedule unsupported scenario images. Inferring an intersection could silently drop requested coverage. A new
configuration file would duplicate compatibility context; workflow feature-name conditions would preserve the current
special case. Explicit selection in the existing test configuration avoids these alternatives.

### Expand the shared scenario matrix by architecture

Scenario entries become `{ feature, arch, runner }`. For every affected feature with scenarios, `buildPlan` emits an
entry for each declared architecture using `RUNNERS`. The existing matrix size check applies after expansion.

The shared job uses `scenarios (${{ matrix.feature }}, ${{ matrix.arch }})` and `matrix.runner`. The feature-test action
continues to receive `mode: scenarios` and the feature id; the native runner determines architecture. The dedicated glab
job disappears, and `ci-gate` depends on the shared scenario job. Its failure/cancellation handling remains unchanged.
No required check is renamed: the required CI entry point remains `ci-gate`.

### Validate each selected architecture

Parameterize scenario image lookup and compatibility checks by architecture. Feature scenario validation uses the
owner's declared scenario architectures, including when checking other in-repo features installed by the scenario. An
installed feature's own scenario selection does not change the compatibility required by the owner's job.

Every scenario with an `image` and no `build` must find that image on the selected architecture in the owner and in
every referenced in-repo feature. Errors identify the scenario, feature, image, and architecture. Schema failures remain
configuration-loading failures; missing feature references retain their existing separate checks.

Global scenario checks continue to use amd64. `build` scenarios keep their existing exemption because their base images
are defined by Dockerfiles rather than the scenario's image field; running them on a newly selected architecture still
requires an actual CI result.

### Synchronize the existing documentation

Update the testing guide, CI job map, workflow header, and affected-script description to describe one scenario job per
feature and selected architecture. The feature scaffold can continue omitting the optional field and inherit amd64, so
it requires no template change. No agent entrypoint or new knowledge file is needed.

## Risks / Trade-offs

- Additional declarations can increase CI cost. Existing files keep the amd64 default, and only glab opts into its
  already-tested second architecture in this change.
- Static compatibility checks cannot prove Dockerfile or external feature support on an architecture. Keep the existing
  build exemption explicit and verify actual jobs in CI.
- Infrastructure paths select canaries and global scenarios under existing rules. Glab is also selected because its test
  configuration changes; inspect `just affected` and report any unexpected selection before proceeding.
- The ordinary amd64 scenario check names gain an architecture suffix. Synchronize the documented names while retaining
  `ci-gate` as the required check and leaving repository settings unchanged.
