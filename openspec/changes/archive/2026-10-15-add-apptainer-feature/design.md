# Design

## Context

See proposal.md for motivation and acceptance; the behavior is in `specs/apptainer/spec.md`. Facts checked on
2026-10-15, needed only for this change:

- **Sources.** Fedora 44 ships `apptainer` and `apptainer-suid` 1.5.4; EPEL 9 ships both for RHEL derivatives, on amd64
  and arm64. Debian 12, Debian 13, Ubuntu 22.04, and Ubuntu 24.04 package nothing. The project's PPA
  (`https://launchpad.net/~apptainer/+archive/ubuntu/ppa`, "Official PPA for Apptainer") publishes `apptainer` 1.5.4 for
  jammy and noble on amd64 and arm64, signed by the key with fingerprint `F6B0F5193D4F3301EF491FF0AFE36534FC6218AE`
  (read from Launchpad's API); its index is served over HTTPS at `ppa.launchpadcontent.net`. The GitHub release v1.5.4
  (2026-09-22) carries `apptainer_1.5.4_amd64.deb`, `apptainer_1.5.4-trixie+_amd64.deb`, the `apptainer-suid`
  counterparts, `.rpm` files for x86_64, and no checksum or signature asset; the same layout holds for v1.4.5. The admin
  guide names the plain `.deb` for Debian 11 and 12 and the `trixie+` one for Debian 13, and sends Ubuntu users to the
  PPA. The Debian 13 package depends on `uidmap`, `fakeroot`, and `libfuse3-4`, and installs
  `/etc/apptainer/apptainer.conf` and the helpers under `/usr/libexec/apptainer/bin` (`squashfuse_ll`, `fuse-overlayfs`,
  `proot`).
- **Docker.** Measured on `fedora:44` with Apptainer 1.5.4 in this repository's docker-in-docker daemon (kernel 6.18, no
  AppArmor): under Docker's default seccomp profile an unprivileged user cannot create a user namespace (`unshare -Ur`
  and `apptainer exec` fail, "not allowed to create user namespace"); with `seccomp=unconfined`, `unshare -Urm` with a
  mount inside succeeds, `apptainer build --sandbox docker://alpine` and `apptainer exec` on the directory succeed,
  `apptainer exec --unsquash docker://alpine` succeeds, `apptainer exec docker://alpine` without `--unsquash` fails with
  "fuse: device /dev/fuse not found" unless the container was started with `--device /dev/fuse`, and `--fakeroot` fails
  in `newgidmap`. Root in the container cannot mount either (no `CAP_SYS_ADMIN`), so a setuid install would gain
  nothing. `apparmor=unconfined` is accepted by a daemon without AppArmor. Docker's `docker-default` AppArmor profile
  denies `mount`, and Ubuntu 24.04 hosts restrict unprivileged user namespaces to confined processes
  (`kernel.apparmor_restrict_unprivileged_userns`), which Apptainer's admin guide tells unprivileged installs to set
  to 0.
- **Slurm.** Slurm's OCI support reads `oci.conf` next to `slurm.conf`; `RunTimeRun` exists since 22.05,
  `IgnoreFileConfigJson`, `EnvExclude`, and `RunTimeEnvExclude` since 23.02. Slurm's documentation runs Singularity with
  `singularity exec --userns %r %@` and Apptainer through a wrapper with `apptainer run`. The backend configuration
  itself belongs to the `slurm` change.

## Goals / Non-Goals

**Goals:**

- One install path per family, each ending in the package manager verifying the package: Fedora
  `dnf install
  apptainer`; RHEL derivative EPEL as the `slurm` change's design states (same `epel-release` route, same
  pinned fingerprint, same `gpg --show-keys --with-colons` check); Ubuntu a `signed-by` source at
  `/etc/apt/sources.list.d/apptainer.sources` naming `/usr/share/keyrings/apptainer-ppa-keyring.gpg`, the key fetched
  with `curl --proto '=https' -fsSL` from the keyserver URL the spec names, checked for exactly one `pub` record with
  the pinned `fpr` in a temporary `GNUPGHOME` removed by a `trap`, and exported by fingerprint alone; Debian the release
  asset resolved through `https://api.github.com/repos/apptainer/apptainer/releases/latest`, downloaded with
  `curl --proto '=https' -fsSL` to a temporary file, installed with `apt-get install ./file.deb` so dependencies
  resolve, and removed — checked by `test.sh` asserting the installed version against the source's candidate
  (`apt-cache
  policy`, `dnf info`, the GitHub tag) and the source file's content on every compatibility image.
- The feature never installs `apptainer-suid`, and `install.sh` names the package explicitly on every path — checked by
  `test.sh` asserting the package is absent and no setuid file exists under `/usr/libexec/apptainer`.
- `securityOpt` holds exactly `seccomp=unconfined` and `apparmor=unconfined` — checked by the autogenerated test
  creating a user namespace with a mount inside as the remote user, which fails under the default profile, and by a
  scenario running a sandbox built from `docker://alpine`.
- Distribution, architecture, and the Debian release are decided before anything changes; prerequisites (`curl`,
  `ca-certificates`, `gnupg`) are installed only where missing — checked by the per-image tests and by the manual
  failure runs.
- The feature changes no host setting and no `apptainer.conf` — checked by review and by `test.sh` comparing the
  package's configuration file with its installed copy.

**Non-Goals:**

- Everything the proposal places out of scope; `NOTES.md` tells users what needs `/dev/fuse` or a host setting.
- Configuring Slurm's `oci.conf` (the `slurm` change does it), `--nv`, `--rocm`, CDI, remote endpoints, or image signing
  keys.
- Ubuntu releases the PPA does not publish for, Debian on arm64 (no upstream package), AlmaLinux 8 and 10, RHEL UBI
  images, openSUSE, Alpine.

## Options

The feature has no options.

- **Rejected option shapes.** A `version` option — rejected for this version: Fedora, EPEL, and the PPA each offer one
  current version, so a pin would hold on Debian alone and mean different things per family; a later change can add it
  with that scope stated. A `suid` option — rejected, the setuid build cannot work in a container without
  `CAP_SYS_ADMIN` and would add a setuid root binary for nothing. A `fuse` option — rejected, a feature cannot add a
  device; the user's `runArgs` can.

## Decisions

- **The project's PPA for Ubuntu, not the GitHub `.deb`.** The PPA is the source the admin guide names for Ubuntu, is
  signed by a key Launchpad publishes with its fingerprint, and ships arm64, which the GitHub release does not.
  Alternative: the GitHub `.deb` on Ubuntu too — rejected, unsigned and amd64 only.
- **The GitHub `.deb` for Debian, relying on TLS.** Debian has no package and the PPA builds for Ubuntu releases only.
  The release platform is GitHub's, the asset is fetched from the release's own URL on every hop over HTTPS, and
  upstream publishes no checksum or signature, which the spec states as the accepted risk. GitHub's asset digest is read
  when present and compared, never required. Alternative: building from the signed source tarball — rejected, the
  tarball is not signed either and the build needs Go. Alternative: dropping Debian — rejected, Debian 12 and 13 are the
  collection's most used images after Ubuntu.
- **`seccomp=unconfined` and `apparmor=unconfined` together.** The seccomp relaxation is the one measurement showed to
  be necessary and sufficient on a host without AppArmor; the AppArmor relaxation lifts `docker-default`'s
  `deny
  mount` on hosts that have it. On Ubuntu 24.04 hosts the restriction on unprivileged user namespaces then
  applies to the unconfined container, and `NOTES.md` names the sysctl Apptainer's guide names. Alternative: a custom
  AppArmor profile shipped by the feature — rejected, a feature cannot load one into the host. Alternative: `privileged`
  — rejected, it grants every capability and device for a runtime that needs none.
- **Non-setuid only.** In a container the setuid helper cannot mount (no `CAP_SYS_ADMIN`), so it would only add a setuid
  root binary and the advisory surface the 1.5.x release notes describe.
- **No `/dev/fuse` handling.** Features cannot add devices. The feature documents `"runArgs": ["--device=/dev/fuse"]`
  and `--unsquash`; it does not set `APPTAINER_UNSQUASH` for everyone, because that changes every run's behavior and
  `containerEnv` cannot depend on the device's presence.

## Risks / Trade-offs

- [The PPA key is rotated or the keyserver changes its URL scheme] → the pinned fingerprint fails the install loudly; a
  later change pins the new key.
- [An Apptainer release changes the `.deb` asset naming or the `trixie+` split] → the Debian path fails naming the asset
  it looked for; the pattern is one constant in `install.sh`.
- [The Ubuntu 24.04 host restriction on unprivileged user namespaces blocks the unconfined container] → documented in
  `NOTES.md` with the sysctl; verified by a manual run on an Ubuntu 24.04 Docker host recorded in the PR, since CI
  runners and this dev container have no AppArmor.
- [A test pulls `docker://alpine` from Docker Hub in CI and meets a rate limit] → the pull is anonymous and small; a
  failure shows as a pull error, not as a false pass.
- [`securityOpt` is new to the collection] → `agent-authority.md` makes it an escalation point; the package gate
  approves it with this design.

## Open Questions

- Whether `apt-get install ./file.deb` on Debian 12 resolves `libfuse3-3` versus `libfuse3-4` without pinning, or the
  plain asset needs `--fix-broken`; a mechanism detail the proof of concept settles.
