# Proposal

Implements [#213](https://github.com/hoshiori-dev/devcontainer-features/issues/213).

## Why

Developers and coding agents in a dev container write and build machine-image templates with HashiCorp Packer, but the
collection has no feature that installs it. Upstream's documented routes for Linux are deb and rpm repositories
configured per family and a manual download; none of them installs a chosen release the same way on every distribution,
and Alpine, openSUSE, and Arch Linux have no upstream repository at all.

## What Changes

- A new feature `packer` installs Packer's `packer` executable from upstream's signed release archives, on `PATH` for
  every user of the container, at the release its `version` option names or the release upstream reports as current.
  Verification checks the release's checksum list against its detached OpenPGP signature by upstream's release key,
  pinned by fingerprint.
- The feature installs no Packer plugin, writes no Packer configuration, sets no environment variable, declares no
  mount, requests no editor extension, and installs no shell completion.
- The feature is installable twice on the same image, with the same or different options.
- `test/packer/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `packer`: installing the `packer` command-line tool, choosing its version, verifying the signed release, installing
  twice, and failing on unsupported platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `packer`, new at version `1.0.0`.
- Files: `src/packer/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/packer/` (`test.sh`, `duplicate.sh`, `checks.sh`, `scenarios.json` with its scenario scripts and
  fixtures, `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated
  row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: no `customizations`, `containerEnv`, `dependsOn`, `installsAfter`, `privileged`, `capAdd`, `securityOpt`,
  `mounts`, `init`, `entrypoint`, or lifecycle command.
- Network at build time: `releases.hashicorp.com`, `www.hashicorp.com`, and, for `latest`,
  `checkpoint-api.hashicorp.com` (design.md, URL inventory), plus the image's configured package repositories for
  missing prerequisites; the feature fetches nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes.
- Security: `latest` is resolved from HashiCorp's Checkpoint service, whose answer upstream does not sign; the delta
  spec states the risk.
- License: Packer 1.10.0 and later are under the Business Source License 1.1. The feature holds the install method only;
  the build downloads the binary from upstream, and the collection redistributes nothing. `NOTES.md` names the license.

## Acceptance

**Becomes true:**

- Every scenario in `specs/packer/spec.md` that a successful container build or a scenario script can show holds on
  every image and architecture in `test/packer/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the
  scenarios; every other scenario holds in the check design.md (Tests) names for it, run once. Each result is recorded
  in the PR's Validation section.
- `test/packer/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/packer/devcontainer-feature.json` has version `1.0.0`, and `src/packer/README.md` and the root `README.md` are
  what `just docs` generates.
- `src/packer/NOTES.md` says how `latest` is chosen and how to pin a release; that plugins are not installed and how to
  install them with `packer init`; how a user keeps plugins and downloads across rebuilds; that Packer contacts
  HashiCorp's Checkpoint service when it runs and how to turn that off; that another `packer` exists at
  `/usr/sbin/packer` on some images; how to set up shell completion; and which license Packer is under.
- `README.zh.md` holds the translated row for `packer` in its feature list.
- `just test packer` and `just test-scenarios packer` pass locally, and the PR's container test jobs pass on amd64 and
  arm64.

**Stays true:**

- The feature has no option that takes a plugin, credential, token, template, or configuration path, and runs no
  `packer` command outside its own install.
- The feature declares no `customizations`, `dependsOn`, `installsAfter`, `mounts`, `capAdd`, `privileged`,
  `securityOpt`, `init`, `entrypoint`, `containerEnv`, or lifecycle command.
- No file outside `src/packer/`, `test/packer/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
