# Proposal

Implements [#188](https://github.com/hoshiori-dev/devcontainer-features/issues/188).

## Why

Godot projects run their tests, imports, and exports from the Godot executable, and editors get GDScript completion from
the language server that the Godot editor itself serves. A dev container for a Godot project therefore needs the engine,
and the collection has no feature that installs it. Developers fall back on unverified downloads in a Dockerfile,
distribution packages that can lag upstream by years, or community images.

## What Changes

- A new feature `godot` installs the standard (GDScript) build of the Godot editor from upstream's verified GitHub
  release archives as `godot`, on `PATH` for every user of the container, at the stable release its `version` option
  names or the latest stable release.
- The feature installs what the official build needs to run without a display on the supported images and nothing for a
  graphical session, so `godot --headless` runs projects, imports, and the GDScript language server in the container;
  platform exports also need export templates, which a user adds as `NOTES.md` shows.
- The feature declares no editor customizations. Its `NOTES.md` shows how a user adds the Godot Tools VS Code extension
  and its headless language server in their own configuration, and what the extension then runs.
- The feature installs no export templates, no .NET build, and no pre-release; its `NOTES.md`, and so its generated
  README, says how to add export templates and that the .NET build is not covered.
- The feature is installable twice on the same image, with the same or different options.
- `test/godot/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `godot`: installing the Godot editor for headless use, choosing its stable release, verifying the download, checking
  that the installed build runs, leaving editor extensions to the user, installing twice, and failing on unsupported
  platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `godot`, new at version `1.0.0`.
- Files: `src/godot/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by `just docs`);
  `test/godot/` (`test.sh`, `duplicate.sh`, `scenarios.json` with its scenario scripts, the `installer.sh` helper and
  the `fixture_curl.sh` stub its failure scenario uses, `compatibility.json`); the root `README.md` (its generated
  feature list) and `README.zh.md` (the translated row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: no `customizations`, `dependsOn`, `installsAfter`, `containerEnv`, `privileged`, `capAdd`, `securityOpt`,
  `mounts`, `init`, `entrypoint`, or lifecycle command.
- Network at build time: `github.com` and the host GitHub's release downloads redirect to (design.md, URL inventory),
  plus the image's configured package repositories when a prerequisite is missing; nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes. Each install downloads one archive of
  about 80 MB.
- Security: upstream publishes a SHA-512 checksum file and no signature, so the archive is verified against the checksum
  file, which relies on TLS alone; the delta spec states it.
- Follow-up outside this change: the .NET build becomes a separate feature with its own issue and change.

## Acceptance

**Becomes true:**

- Every scenario in `specs/godot/spec.md` that a successful container build can show holds on every image and
  architecture in `test/godot/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios; every
  other scenario holds in the check design.md (Goals) names for it, run once. Each result is recorded in the PR's
  Validation section.
- `test/godot/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/godot/devcontainer-feature.json` has version `1.0.0`, and `src/godot/README.md` and the root `README.md` are what
  `just docs` generates.
- `src/godot/NOTES.md` states that the feature is for headless use and installs nothing for a graphical session; shows
  how to add the Godot Tools extension and turn on its headless language server in the user's own `customizations`, and
  says that the extension then runs, on every activation, the executable that the opened workspace's settings may
  choose, and starts the Godot editor on the workspace's project, which runs the project's editor plugins and tool
  scripts; tells users to pin `version` to their project's release; shows how to install export templates for the
  installed version from the same GitHub release, verified against its `SHA512-SUMS.txt`, and where Godot looks for
  them; and says that the .NET build and pre-releases are not covered.
- `README.zh.md` holds the translated row for `godot` in its feature list.
- `just test godot` and `just test-scenarios godot` pass locally, and the PR's container test jobs pass on amd64 and
  arm64.

**Stays true:**

- The feature has no option that takes a credential, a token, a URL, or a path.
- The feature declares no `customizations`, `dependsOn`, `installsAfter`, `mounts`, `capAdd`, `privileged`,
  `securityOpt`, `init`, `entrypoint`, or lifecycle command.
- No file outside `src/godot/`, `test/godot/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
