# Proposal

Implements [#194](https://github.com/hoshiori-dev/devcontainer-features/issues/194).

## Why

Developers and coding agents in a dev container often need to move data between the container and cloud storage:
datasets, build artifacts, backups, or a remote bucket mounted as a directory. rclone does this for most storage
providers through one command, but the collection has no feature that installs it. Upstream's documented one-liner pipes
an installer into a shell without verifying anything, and distribution packages lag behind upstream releases.

## What Changes

- A new feature `rclone` installs the `rclone` executable from upstream's signed release archives, on `PATH` for every
  user of the container, at the release its `version` option names or the newest stable release. Verification checks the
  release's signed checksum list against upstream's release key, pinned by fingerprint.
- The feature installs bash, zsh, and fish completion scripts generated by the installed `rclone`, so they always match
  its version. It installs none of the shells or completion frameworks.
- Its `installMountDependencies` option, when enabled, installs the FUSE helper `rclone mount` needs. The feature never
  grants the container the privileges a mount needs; its `NOTES.md`, and so its generated README, names the container
  settings a mount needs and what a mount by a non-root user needs on top of them.
- The feature writes no rclone configuration and stores no credential.
- The feature is installable twice on the same image, with the same or different options.
- `test/rclone/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `rclone`: installing the rclone command-line tool, choosing its version, verifying the signed release, installing its
  shell completions and, on request, its FUSE mount helper, installing twice, and failing on unsupported platforms or
  failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `rclone`, new at version `1.0.0`.
- Files: `src/rclone/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/rclone/` (`test.sh`, `duplicate.sh`, `checks.sh`, `scenarios.json` with its scenario scripts and
  fixtures, `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated
  row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: no `containerEnv`, `dependsOn`, `installsAfter`, `privileged`, `capAdd`, `securityOpt`, `mounts`, `init`,
  `entrypoint`, or lifecycle command.
- Network at build time: `downloads.rclone.org` and `rclone.org` (design.md, URL inventory), plus the image's configured
  package repositories for missing prerequisites and the FUSE helper; nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes.
- Security: upstream signs the checksum list with a DSA-1024 key using SHA-1 digests, and publishes the newest-version
  file unsigned; the delta spec states both risks.

## Acceptance

**Becomes true:**

- Every scenario in `specs/rclone/spec.md` that a successful container build or a scenario script can show holds on
  every image and architecture in `test/rclone/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the
  scenarios; every other scenario holds in the check design.md (Goals) names for it, run once. Each result is recorded
  in the PR's Validation section.
- `test/rclone/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/rclone/devcontainer-feature.json` has version `1.0.0`, and `src/rclone/README.md` and the root `README.md` are
  what `just docs` generates.
- `src/rclone/NOTES.md` names the container settings `rclone mount` needs, what a non-root mount needs on top of them,
  how to bring an existing rclone configuration into the container, and that `rclone selfupdate` replaces the binary the
  feature manages.
- `README.zh.md` holds the translated row for `rclone` in its feature list.
- `just test rclone` and `just test-scenarios rclone` pass locally, and the PR's container test jobs pass on amd64 and
  arm64.

**Stays true:**

- The feature has no option that takes a remote definition, credential, token, or configuration path, and starts no
  transfer, mount, or `rclone` process outside its own install.
- The feature declares no `dependsOn`, `installsAfter`, `mounts`, `capAdd`, `privileged`, `securityOpt`, `init`,
  `entrypoint`, `containerEnv`, or lifecycle command.
- No file outside `src/rclone/`, `test/rclone/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
