# Proposal

Implements [#200](https://github.com/hoshiori-dev/devcontainer-features/issues/200).

## Why

Developers and coding agents in a dev container often write and apply infrastructure-as-code configurations, and
OpenTofu is the open-source tool for that, but the collection has no feature that installs it. Upstream's documented
routes are an installer script, distribution repositories configured per family, and an Alpine package only in the
`edge` repository; none of them installs a chosen release the same way on every distribution.

## What Changes

- A new feature `opentofu` installs OpenTofu's `tofu` executable from upstream's signed release archives, on `PATH` for
  every user of the container, at the release its `version` option names or the release upstream marks as latest.
  Verification checks the release's checksum list against its detached OpenPGP signature by upstream's release key,
  pinned by fingerprint.
- The feature requests upstream's VS Code extension, `opentofu.vscode-opentofu`.
- The feature writes no OpenTofu configuration, credential, or environment variable, installs no `terraform` command,
  and installs no shell completion.
- The feature is installable twice on the same image, with the same or different options.
- `test/opentofu/` tests the feature on the images and architectures its compatibility list names.
- The root `README.md` gains the feature's row in its generated list, and `README.zh.md` carries the same row in
  Chinese.

## Capabilities

### New Capabilities

- `opentofu`: installing the `tofu` command-line tool, choosing its version, verifying the signed release, requesting
  the editor extension, installing twice, and failing on unsupported platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `opentofu`, new at version `1.0.0`.
- Files: `src/opentofu/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/opentofu/` (`test.sh`, `duplicate.sh`, `checks.sh`, `scenarios.json` with its scenario scripts and
  fixtures, `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated
  row).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Metadata: `customizations.vscode.extensions` only; no `containerEnv`, `dependsOn`, `installsAfter`, `privileged`,
  `capAdd`, `securityOpt`, `mounts`, `init`, `entrypoint`, or lifecycle command.
- Network at build time: `github.com` with GitHub's release asset host, and `get.opentofu.org` (design.md, URL
  inventory), plus the image's configured package repositories for missing prerequisites; nothing at container start.
- CI: the PR runs the feature's container tests on every image and architecture of its compatibility list and its
  scenarios on both architectures, through the existing jobs; no workflow changes.
- Security: `latest` is resolved from GitHub's latest-release link, which upstream does not sign; the delta spec states
  the risk.

## Acceptance

**Becomes true:**

- Every scenario in `specs/opentofu/spec.md` that a successful container build or a scenario script can show holds on
  every image and architecture in `test/opentofu/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the
  scenarios; every other scenario holds in the check design.md (Tests) names for it, run once. Each result is recorded
  in the PR's Validation section.
- `test/opentofu/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/opentofu/devcontainer-feature.json` has version `1.0.0`, and `src/opentofu/README.md` and the root `README.md`
  are what `just docs` generates.
- `src/opentofu/NOTES.md` says how `latest` is chosen and how to pin a release, how to exclude the editor extension,
  that `git::` module sources need git, and how a user sets up a provider plugin cache or shell completion themselves.
- `README.zh.md` holds the translated row for `opentofu` in its feature list.
- `just test opentofu` and `just test-scenarios opentofu` pass locally, and the PR's container test jobs pass on amd64
  and arm64.

**Stays true:**

- The feature has no option that takes a backend, credential, token, provider, or configuration path, and runs no `tofu`
  command outside its own install.
- The feature declares no `dependsOn`, `installsAfter`, `mounts`, `capAdd`, `privileged`, `securityOpt`, `init`,
  `entrypoint`, `containerEnv`, or lifecycle command.
- No file outside `src/opentofu/`, `test/opentofu/`, the root `README.md`, `README.zh.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
