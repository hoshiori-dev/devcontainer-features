# Proposal

This file describes the baseline implementation. The same PR also carries ../configure-pacman-packages-cleanup/, a
separate phase 1 extension approved in conversation on 2026-10-04 and implemented in this first release. Its delta
supersedes the relevant baseline requirements only when applied; the baseline task completion and test results do not
validate its new paths.

Implements [#23](https://github.com/hoshiori-dev/devcontainer-features/issues/23).

## Why

A dev container on Arch Linux that needs a few extra system packages today needs a Dockerfile, or a broader feature that
also adds repositories and configures the system. The collection has no feature that only installs a list of packages
with `pacman`. `pacman-packages` is one of five atomic installers, one per package manager (`apt-packages`,
`dnf-packages`, `apk-packages`, `pacman-packages`, `zypper-packages`), which share one option shape and one script
skeleton, and each of which keeps its package manager's own behavior.

## What Changes

- A new feature `pacman-packages` installs the system packages named in one option with `pacman`, from the repositories
  the image already configures, and nothing else: no repositories, mirrors, keys, or pacman configuration of its own.
  Its contract is `specs/pacman-packages/spec.md`.
- A non-empty list also upgrades the whole system (requirement "Full system upgrade"). Issue #23 lists upgrading the
  whole system as out of scope; the maintainer approved this exception for `pacman-packages`, and the spec and
  `NOTES.md` state it.
- `pacman` may fetch a missing or expired packager key into the image's keyring (requirement "Packager key import").
  Issue #23 lists "adding third-party repositories or keys" as out of scope; the maintainer accepted the import as
  `pacman`'s own behavior (`design.md`, Open question 1), and the spec and `NOTES.md` state it.
- The root `README.md` lists `pacman-packages` under "Features": one row with the id linked to `src/pacman-packages/`
  and a one-sentence description. If no other feature has been listed yet, this row replaces the line "No features have
  been published yet."

## Capabilities

### New Capabilities

- `pacman-packages`: installing a list of system packages with `pacman` from the image's configured repositories, as
  part of a full system upgrade.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `pacman-packages`, new, first published at version `1.0.0`. No other feature changes, and none
  depends on it, so CI tests only `pacman-packages`.
- Files: `src/pacman-packages/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/pacman-packages/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` with its
  scenario scripts, and the direct checks named in `design.md`, Test plan); `openspec/specs/pacman-packages/spec.md`,
  created when the change is archived; the root `README.md` (one row under "Features").
- `test/canary.json` does not change; canary membership is left to the maintainer.
- Supported images: the planned compatibility list is in `design.md` (Supported images); `test/pacman-packages/`
  `compatibility.json` becomes its source of truth. Arch Linux publishes no official arm64 image, so the list is amd64
  only.
- No script, workflow, test infrastructure, or knowledge file changes.

## Acceptance

**Becomes true:**

- Every scenario in `specs/pacman-packages/spec.md` passes in the test named for it in `design.md` (Test plan), and the
  PR's Validation section names each scenario with its test, image, architecture, and result:
  - scenario tests (`just test-scenarios pacman-packages`) run in CI on amd64, each on the image its `scenarios.json`
    entry names;
  - the autogenerated and install-twice tests (`just test pacman-packages`) run in CI on every image and architecture in
    `test/pacman-packages/compatibility.json`;
  - the direct checks under `test/pacman-packages/` run locally on every image in that list and on the pinned image
    outside it that `design.md` (Test plan) names, and their output is recorded in the Validation section; CI does not
    run them.
- The issue's acceptance sketch is covered by the scenarios "Listed packages are installed", "Image without pacman fails
  clearly", and "Different list on the second install".
- `test/pacman-packages/compatibility.json` lists exactly the images and architectures planned in `design.md`.
- `src/pacman-packages/devcontainer-feature.json` has version `1.0.0` and a single option, `packages`; `just check`
  passes, including the README generated by `just docs`.
- `src/pacman-packages/NOTES.md` states that a non-empty list upgrades the whole system, including replacing packages
  that the repositories declare replaced, and that `pacman` may fetch a missing or expired packager key into the image's
  keyring, from hosts Arch Linux does not run, where it stays without gaining trust.
- The root `README.md` has one row for `pacman-packages` under "Features", with the id linked to `src/pacman-packages/`
  and a one-sentence description, and no longer reads "No features have been published yet."; this is a hand edit,
  separate from `src/pacman-packages/README.md`, which `just docs` generates.

**Stays true:**

- The feature fetches nothing itself: `install.sh` contains no URL and no download tool, and every package comes from
  the repositories configured in the image.
- The feature never disables or weakens signature checking and itself adds, removes, or edits no repository, mirror,
  key, or pacman configuration file, except packager keys `pacman` fetches (scenarios under "Repository authentication
  stays in effect" and "Packager key import").
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, or lifecycle commands.
- No file outside `src/pacman-packages/`, `test/pacman-packages/`, `openspec/`, and the root `README.md` changes; every
  required check passes on the PR.
