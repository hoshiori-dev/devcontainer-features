# Proposal

Implements [#24](https://github.com/hoshiori-dev/devcontainer-features/issues/24).

## Why

A dev container on openSUSE that needs a few extra system packages today needs a Dockerfile, or a broader feature that
also adds repositories and configures the system. The collection has no feature that only installs a list of packages
with `zypper`. `zypper-packages` is one of five atomic installers, one per package manager (`apt-packages`,
`dnf-packages`, `apk-packages`, `pacman-packages`, `zypper-packages`), which share one option shape and one script
skeleton, and each of which keeps its package manager's own behavior.

## What Changes

- A new feature `zypper-packages` installs the system packages named in packages with explicit installation controls
  with `zypper`, from the repositories the image already configures, with selectable dependency, refresh, and cleanup
  policies: no repositories, keys, services, or zypp configuration of its own. Its contract is
  `specs/zypper-packages/spec.md`.
- The repository's root `README.md` lists the feature: one row under "## Features" with the id `zypper-packages` linking
  to `src/zypper-packages/` and a one-sentence description; when it is the section's first row, it replaces the line "No
  features have been published yet.". This is separate from the feature's own generated `src/zypper-packages/README.md`.
- The issue's outcome names openSUSE and SLE. This change supports and tests openSUSE images only; SUSE Linux Enterprise
  images are planned as a follow-up MINOR change (`design.md`, Open question 5).

## Capabilities

### New Capabilities

- `zypper-packages`: installing a list of system packages with `zypper` from the image's configured repositories.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `zypper-packages`, new, first published at version `1.0.0`. No other feature changes, and none
  depends on it, so CI tests only `zypper-packages`.
- Files: `src/zypper-packages/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/zypper-packages/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` with its
  scenario scripts, and the direct checks named in `design.md`, Test plan); `openspec/specs/zypper-packages/spec.md`,
  created when the change is archived; the root `README.md` (one row under "## Features").
- Supported images: the planned compatibility list is in `design.md` (Supported images);
  `test/zypper-packages/compatibility.json` becomes its source of truth.
- No script, workflow, test infrastructure, or knowledge file changes.
- `test/canary.json` is not changed; whether the feature joins it is left to the maintainer.

The phase 1 controls are part of this first release at 1.0.0. Defaults preserve the earlier package; the expanded
approval package requires fresh review before tasks or implementation. No other feature or compatibility image changes.

## Acceptance

**Becomes true:**

- The option and interaction scenarios for phase 1 in the delta spec pass on each supported package-manager generation;
  invalid controls fail before any package-manager call, defaults preserve baseline behavior, and repeated invocations
  use their own values.
- The design's phase 1 verification bounds are covered by scenario and direct checks, with results recorded in the PR.
- Metadata, documentation, and the generated README describe every declared option consistently.

- Every scenario in `specs/zypper-packages/spec.md` passes in the test named for it in `design.md` (Test plan), and the
  PR's Validation section names each scenario with its test, image, architecture, and result:
  - scenario tests (`just test-scenarios zypper-packages`) run in CI on amd64, each on the image its `scenarios.json`
    entry names;
  - the autogenerated and install-twice tests (`just test zypper-packages`) run in CI on every image and architecture in
    `test/zypper-packages/compatibility.json`;
  - the direct checks under `test/zypper-packages/` run locally on every amd64 image in that list and on the pinned
    image outside it that `design.md` (Test plan) names, and their output is recorded in the Validation section; CI does
    not run them. The one exception is "Pin below the installed version on the second install" on `opensuse/tumbleweed`,
    which needs a package offered in two versions (`design.md`, Test plan): when none is offered at validation time, the
    Validation section records the check as not run on that image.
- The issue's acceptance sketch is covered by the scenarios "Listed packages are installed", "Image without zypper fails
  clearly", and "Different list on the second install", on openSUSE images; SLE is outside this change.
- `test/zypper-packages/compatibility.json` lists exactly the images and architectures planned in `design.md`.
- `src/zypper-packages/devcontainer-feature.json` has version `1.0.0` and the options declared by its delta spec;
  `just check` passes, including the README generated by `just docs`.
- The root `README.md` has, under "## Features", one row for `zypper-packages` whose id links to `src/zypper-packages/`
  and which gives a one-sentence description, and the section no longer says "No features have been published yet.".

**Stays true:**

- The feature fetches nothing itself: `install.sh` contains no URL and no download tool, and every package comes from
  the repositories configured in the image.
- The feature never disables or weakens signature checking, never trusts a key on its own, and itself adds, removes, or
  edits no repository, service, key, or zypp configuration file (scenarios under "Repository authentication stays in
  effect").
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, or lifecycle commands.
- No file outside `src/zypper-packages/`, `test/zypper-packages/`, `openspec/`, and the root `README.md` changes; every
  required check passes on the PR.
