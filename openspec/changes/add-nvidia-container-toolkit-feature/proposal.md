# Proposal

Implements [#15](https://github.com/hoshiori-dev/devcontainer-features/issues/15).

## Why

A dev container that runs its own container engine, for example through docker-in-docker, on a GPU host cannot give the
containers it starts access to the GPUs: that needs the NVIDIA Container Toolkit inside the dev container and, when
Docker is the engine, the NVIDIA runtime registered with the daemon. Doing this by hand in every `devcontainer.json`
means adding NVIDIA's package repository, trusting its signing key, pinning four packages to one version, and editing
`/etc/docker/daemon.json`, each of which is easy to get wrong in ways that fail silently.

## What Changes

- A new feature `nvidia-container-toolkit` installs the NVIDIA Container Toolkit (`nvidia-ctk` and its companion
  packages) from NVIDIA's stable package repository, trusting only NVIDIA's signing key identified by its full
  fingerprint, on the Debian, Ubuntu, Fedora, and openSUSE images listed in its compatibility list.
- A `version` option installs either the newest stable release or one exact release for every toolkit package. Every
  release the stable repository offers stays installable, including older ones with known vulnerabilities; the feature's
  `NOTES.md` warns about them, leaves that risk to the user who pins a version, and points to NVIDIA's security
  bulletins as the authoritative source.
- A `configureDocker` option registers the `nvidia` runtime with a Docker daemon installed in the dev container.
- The feature is ordered after the docker-in-docker feature, so a daemon that feature installs is configured.
- The feature can be installed twice, with the same or different options.
- The repository's root `README.md` lists the feature under "Features": one row whose id links to
  `src/nvidia-container-toolkit/`, with a one-sentence description; if the section still holds "No features have been
  published yet.", the row replaces that line.
- Installing GPU drivers or CUDA, exposing the host's GPUs to the dev container itself, and testing on real GPUs stay
  out of scope.

## Capabilities

### New Capabilities

- `nvidia-container-toolkit`: installing the NVIDIA Container Toolkit from NVIDIA's signed repository, the `version` and
  `configureDocker` options, Docker runtime registration, repeated installation, and failure behavior.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `nvidia-container-toolkit`, new at version `1.0.0`. No other feature changes, so no other bump.
- Files: `src/nvidia-container-toolkit/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, generated `README.md`),
  `test/nvidia-container-toolkit/` (`test.sh`, `duplicate.sh`, `scenarios.json` and its scripts, `compatibility.json`),
  and `openspec/specs/nvidia-container-toolkit/spec.md` at archive; the root `README.md` gains the feature's row under
  "Features".
- Security: older toolkit releases with known vulnerabilities, including container escapes, can be installed through
  `version`; the user who pins one carries that risk, as the maintainer decided on
  [PR #29](https://github.com/hoshiori-dev/devcontainer-features/pull/29#issuecomment-5909346162). The default `latest`
  and the `proposals` entry `1.19.1` are outside the known vulnerable ranges.
- `test/canary.json` does not change; canary membership is left to the maintainer.
- Dependencies: `installsAfter` the external feature `ghcr.io/devcontainers/features/docker-in-docker`; no `dependsOn`.
- CI: the new feature's jobs on each compatibility image, and one scenario job running its scenarios, among them one
  that installs it together with docker-in-docker.

## Acceptance

**Becomes true:**

- The scenarios of the requirements "Install the toolkit from NVIDIA's stable repository" and "Register the NVIDIA
  runtime with Docker" (except "Invalid daemon settings file"), the "Latest version", "Exact version", and "Older
  release with known vulnerabilities" scenarios of "Choose the toolkit version", and the "Same options twice" and
  "Different version the second time" (older exact version, then `latest`) scenarios of "Installing twice" pass in the
  feature's autogenerated, duplicate, or scenario tests on every image of
  `test/nvidia-container-toolkit/compatibility.json` they apply to.
- The scenarios CI cannot run are each verified by a manual run recorded in the PR's Validation section: those of "Trust
  only NVIDIA's pinned signing key" and "Unsupported platforms fail the build"; "Version the repository does not offer"
  and "Malformed version"; "Invalid daemon settings file"; "Docker configured twice" and "Docker configuration disabled
  the second time"; and "Different version the second time" from `latest` to an older exact version, on one image of
  each package-manager family.
- `src/nvidia-container-toolkit/NOTES.md` says that older toolkit releases have known vulnerabilities, including
  container escapes, and that users who pin an exact `version` judge that risk themselves; lists the vulnerable ranges
  known at release time, at least those in the maintainer's
  [decision on PR #29](https://github.com/hoshiori-dev/devcontainer-features/pull/29#issuecomment-5909346162) — fixed in
  1.16.2 (CVE-2024-0132 critical, CVE-2024-0133 medium), 1.17.3 (CVE-2024-0135 high, CVE-2024-0136 high, CVE-2024-0137
  medium), 1.17.4 (CVE-2025-23359 high), and 1.17.8 (CVE-2025-23266 critical, CVE-2025-23267 high); and links NVIDIA's
  product security page, https://www.nvidia.com/en-us/security/, as the authoritative, current source.
- `just check` passes, including `just validate` for the new feature's metadata, version `1.0.0`, and compatibility
  list, and `just docs` leaves the generated `src/nvidia-container-toolkit/README.md` unchanged.
- The root `README.md` has one row for `nvidia-container-toolkit` under "## Features", linking to
  `src/nvidia-container-toolkit/` with a one-sentence description, and no longer says "No features have been published
  yet.".
- `just test nvidia-container-toolkit` and `just test-scenarios nvidia-container-toolkit` pass locally.

**Stays true:**

- The feature adds no `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`, `containerEnv`, or
  lifecycle commands to the dev container, and does not install GPU drivers or CUDA.
- NVIDIA's signing key is authenticated by its pinned fingerprint, and everything from NVIDIA's repository by a
  signature from that key, before it is used; the prerequisites (`curl`, `ca-certificates`, `gnupg`/`gpg2`) come from
  the image's own repositories and are verified by its package manager.
- No other feature's files, version, or tests change.
