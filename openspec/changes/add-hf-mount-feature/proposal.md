# Proposal

Implements [#18](https://github.com/hoshiori-dev/devcontainer-features/issues/18).

## Why

Hugging Face Buckets and repositories are often larger than a dev container should hold, and `hf-mount` mounts them as
local filesystems that fetch data on demand. Upstream ships prebuilt Linux binaries and a Homebrew formula but no apt or
dnf package, so each consumer would otherwise script the download, the architecture choice, the mount helpers, and the
verification themselves.

## What Changes

- A new feature `hf-mount` installs the upstream `hf-mount` daemon on glibc-based images, on x86_64 and aarch64,
  together with the NFS backend, the FUSE backend, or both, as the `backend` option selects.
- The `version` option pins an upstream release or follows the latest one; downloads are verified as the spec's download
  requirement states.
- The `installMountDependencies` option decides whether the selected backends' mount helpers are installed.
- The feature installs tools only; its notes name the container settings a mount needs.
- A second install behaves as the spec's Installing twice requirement states.
- The repository's root `README.md` lists `hf-mount` under "Features" with a one-sentence description, as the
  collection's first published feature.

## Capabilities

### New Capabilities

- `hf-mount`: installing the `hf-mount` daemon and its NFS and FUSE backends from upstream releases, with verified
  downloads and optional mount dependencies.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `hf-mount`, new, first published at version `1.0.0`.
- Files: `src/hf-mount/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and the `README.md` that `just docs`
  generates), `test/hf-mount/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` and its scripts), and
  `openspec/specs/hf-mount/spec.md` once the change is archived.
- Root `README.md`: one row for `hf-mount` under "## Features", replacing "No features have been published yet.".
- `test/canary.json` is not changed; canary membership is left to the maintainer.
- Upstream dependency: releases of `huggingface/hf-mount` on GitHub and the GitHub Releases API; the design records the
  URL inventory and the verification trade-off.
- CI: the feature's container tests run for every compatibility image and architecture, plus one scenario job.

## Acceptance

**Becomes true:**

- On every image and architecture in `test/hf-mount/compatibility.json`, the default install and the install-twice test
  pass (`just test hf-mount` locally and the PR's container jobs): they show the scenarios "Omitted version" (the
  container test asserts the `hf-mount <MAJOR.MINOR.PATCH>` form and makes no API request), "Omitted backend", "Omitted
  installMountDependencies", "The installed daemon runs", "Digest matches", "Token absent", "NFS dependencies", "FUSE
  dependencies", "Container starts with no mount", and "Non-default options, then the defaults". Root and non-root runs
  are covered by the images whose entry does and does not name a `remoteUser`.
- On amd64, one scenario per case passes on its scenario image (`just test-scenarios hf-mount` and the PR's scenario
  job): "Only the NFS backend selected", "Only the FUSE backend selected", "Dependencies disabled", and "Pinned
  release".
- Every other scenario of `specs/hf-mount/spec.md` is shown once by hand and recorded in the PR's Validation section:
  "Malformed version" (`v0.13.1` and `0.13`), "Release does not exist", "Digest does not match", "Digest missing or
  malformed", "Asset missing from the release", "HTTP error", "Token present" and "Token rejected" (a dummy
  `GITHUB_TOKEN` set as an image `ENV`), "Rate limit reached", "musl-based image", "glibc too old", "Unsupported
  architecture", "Unsupported distribution", "Same options twice", "A backend not selected the second time", and "Older
  version the second time"; the design names how each is provoked.
- One mount of a small public Hugging Face repository per backend, with the `runArgs` that `NOTES.md` names, succeeds by
  hand and is recorded in the PR's Validation section.
- `src/hf-mount/README.md` is generated by `just docs` and documents every option; `NOTES.md` names the container
  settings a mount needs, the non-root prerequisites, and what the download verification does and does not prove.
- The root `README.md` has, under "## Features", one row for `hf-mount` — the id linking to `src/hf-mount/` and a
  one-sentence description — in place of "No features have been published yet."; this is separate from the generated
  `src/hf-mount/README.md`.
- `just check` passes, including `just spec-check` on this change.

**Stays true:**

- No feature, file, or setting outside `src/hf-mount/`, `test/hf-mount/`, this change, and `openspec/specs/hf-mount/`
  (created at archive) is altered, except the `hf-mount` row in the root `README.md`; `test/canary.json` stays as it is.
- The feature's metadata adds no `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`, `containerEnv`,
  lifecycle command, `dependsOn`, or `installsAfter`.
- No credential, token, or personal data enters a file, option, commit, or build log.
- Every required check passes on this PR.
