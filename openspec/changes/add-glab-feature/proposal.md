# Proposal

Implements [#13](https://github.com/hoshiori-dev/devcontainer-features/issues/13).

## Why

A dev container that works against GitLab needs the GitLab CLI (`glab`), and the collection has no feature that installs
it. Installing it by hand in every Dockerfile repeats the download, the checksum check, and the architecture mapping,
and tempts people to pass a token at build time, where it ends up in build logs that get pasted into bug reports and
assistant chats.

## What Changes

- A new feature `glab` installs the GitLab CLI from upstream's verified release artifacts, on `PATH` for every user of
  the container, at the version its `version` option names or the latest release.
- The feature is installable twice on the same image, with the same or a different `version`.
- The feature configures no authentication: it has no login, token, or GitLab-host option and writes no glab
  configuration. Users authenticate after the container starts, with glab's own commands or environment variables they
  manage outside the feature.
- `test/glab/` tests the feature on the images and architectures its compatibility list names.
- The repository's root `README.md` lists `glab` under "## Features": one row with the id linking to `src/glab/` and a
  one-sentence description, replacing "No features have been published yet.". This is separate from the feature's own
  `src/glab/README.md`, which `just docs` generates.

## Capabilities

### New Capabilities

- `glab`: installing the GitLab CLI, choosing its version, verifying the download, installing twice, and failing on
  unsupported platforms or failed verification.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `glab`, new at version `1.0.0`.
- Files: `src/glab/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by `just docs`);
  `test/glab/` (`test.sh`, `duplicate.sh`, `scenarios.json` with its scenario scripts, `compatibility.json`); the root
  `README.md` (its Features row, as named under What Changes).
- `test/canary.json` is not touched: canary membership is left to the maintainer.
- Network at build time: `gitlab.com` (design.md, URL inventory), plus the image's configured package repositories when
  a prerequisite is missing; nothing at container start.
- CI: the PR runs `glab`'s container tests on every image and architecture of its compatibility list.

## Acceptance

**Becomes true:**

- Every scenario in `specs/glab/spec.md` that a successful container build can show holds on every image and
  architecture in `test/glab/compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios; every other
  scenario holds in the manual check design.md (Goals) names for it, run once. Each result is recorded in the PR's
  Validation section.
- `test/glab/compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- `src/glab/devcontainer-feature.json` has version `1.0.0`, and `src/glab/README.md` is what `just docs` generates.
- `just test glab` and `just test-scenarios glab` pass locally, and the PR's container test jobs pass on amd64 and
  arm64.
- The root `README.md` holds, under "## Features", exactly one row, for `glab`: the id linking to `src/glab/` and a
  one-sentence description; "No features have been published yet." is gone.

**Stays true:**

- The feature has no option that takes a credential, token, or GitLab host, and no build step logs one.
- The feature declares no `mounts`, `capAdd`, `privileged`, `securityOpt`, `init`, `entrypoint`, or lifecycle command.
- No file outside `src/glab/`, `test/glab/`, the root `README.md`, and this change changes.
- `just check` passes, and every required check passes on this PR.
