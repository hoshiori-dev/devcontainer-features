# Proposal

Implements [#21](https://github.com/hoshiori-dev/devcontainer-features/issues/21).

## Why

A dev container on Fedora, RHEL, or one of its rebuilds that needs a few extra system packages today needs a Dockerfile,
or a broader feature that also adds repositories and configures the system. The collection has no feature that only
installs a list of packages with `dnf`. `dnf-packages` is one of five atomic installers, one per package manager
(`apt-packages`, `dnf-packages`, `apk-packages`, `pacman-packages`, `zypper-packages`), which share one option shape and
one script skeleton, and each of which keeps its package manager's own behavior.

## What Changes

- A new feature `dnf-packages` installs the system packages named in one option with `dnf`, from the repositories the
  image already configures and enables, and nothing else: no repositories, keys, or dnf configuration of its own. Its
  contract is `specs/dnf-packages/spec.md`.
- The repository's root `README.md` lists `dnf-packages` under "## Features": one row with the id linking to
  `src/dnf-packages/` and a one-sentence description; as the first row, it replaces "No features have been published
  yet."

## Capabilities

### New Capabilities

- `dnf-packages`: installing a list of system packages with `dnf` from the image's enabled repositories.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `dnf-packages`, new, first published at version `1.0.0`. No other feature changes, and none
  depends on it, so CI tests only `dnf-packages`.
- Files: `src/dnf-packages/` (`devcontainer-feature.json`, `install.sh`, `NOTES.md`, and `README.md` generated by
  `just docs`); `test/dnf-packages/` (`compatibility.json`, `test.sh`, `duplicate.sh`, `scenarios.json` with its
  scenario scripts, and the direct checks named in `design.md`, Test plan); `openspec/specs/dnf-packages/spec.md`,
  created when the change is archived; the root `README.md`, "## Features" section only.
- `test/canary.json` is unchanged; canary membership is left to the maintainer.
- Supported images: the planned compatibility list is in `design.md` (Supported images); `test/dnf-packages/`
  `compatibility.json` becomes its source of truth.
- No script, workflow, test infrastructure, or knowledge file changes.
- The issue's outcome names Fedora, RHEL, and its rebuilds. This change supports and tests Fedora and two RHEL 9
  rebuilds; Red Hat's own images and the RHEL 10 generation are planned as a follow-up MINOR change (`design.md`, Open
  question 7).

## Acceptance

**Becomes true:**

- Every scenario in `specs/dnf-packages/spec.md` passes in the test named for it in `design.md` (Test plan), and the
  PR's Validation section names each scenario with its test, image, architecture, and result:
  - scenario tests (`just test-scenarios dnf-packages`) run in CI on amd64, each on the image its `scenarios.json` entry
    names;
  - the autogenerated and install-twice tests (`just test dnf-packages`) run in CI on every image and architecture in
    `test/dnf-packages/compatibility.json`;
  - the direct checks under `test/dnf-packages/` run locally on every amd64 image in that list and on the images outside
    it that `design.md` (Test plan) names for them, and their output is recorded in the Validation section; CI does not
    run them.
- The issue's acceptance sketch is covered by the scenarios "Listed packages are installed", "Image without dnf fails
  clearly", and "Different list on the second install".
- `test/dnf-packages/compatibility.json` lists exactly the images and architectures planned in `design.md`.
- The root `README.md`'s "## Features" section has exactly one row for `dnf-packages`, its id linking to
  `src/dnf-packages/` and a one-sentence description, and no longer holds "No features have been published yet."; this
  row is separate from the generated `src/dnf-packages/README.md`.
- `src/dnf-packages/devcontainer-feature.json` has version `1.0.0` and a single option, `packages`; `just check` passes,
  including the README generated by `just docs`.

**Stays true:**

- The feature fetches nothing itself: `install.sh` contains no URL and no download tool, and every package comes from
  the repositories configured and enabled in the image.
- Signature checking and the image's repositories, keys, and `dnf` configuration: the scenarios under "Package signature
  checking stays in effect", including the key import `dnf` may perform.
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, or lifecycle commands.
- No file outside `src/dnf-packages/`, `test/dnf-packages/`, `openspec/`, and the root `README.md`'s "## Features"
  section changes; every required check passes on the PR.
