# Proposal

Implements [#202](https://github.com/hoshiori-dev/devcontainer-features/issues/202).

## Why

Developers who build machine images, test installers, or work on infrastructure code need virtual machines next to their
source. libvirt is the usual way to manage them on Linux, but the collection has no feature for it, and running libvirt
in or beside a container takes several settings that are easy to get wrong: which socket the client reaches, who may
open it, and how the daemon starts without systemd.

## What Changes

- A new feature `libvirt-outside-of-docker` installs the libvirt client tools (`virsh`, and by default `virt-install`)
  and prepares the dev container to manage the virtual machines of the host: it makes `qemu:///system` the default
  connection and, at every container start, lets the remote user open the host's libvirt socket when the developer has
  mounted the host's `/run/libvirt` into the container. The feature declares no mount itself, so a container with it
  also starts on a host without libvirt.
- A new feature `libvirt-in-docker` installs the libvirt daemon, QEMU, UEFI firmware, and the client tools into the dev
  container, declares the container privileged, and starts the daemon at every container start. The remote user manages
  virtual machines that run inside the dev container, with KVM when the host offers it and software emulation otherwise.
  Their definitions and disks live on two named volumes and survive a rebuild.
- The two features are alternatives: installing both fails the build.
- Both install only the image's distribution packages and download nothing else.
- Both are installable twice on the same image, with the same or different options.
- `test/libvirt-outside-of-docker/` and `test/libvirt-in-docker/` test the features on the images and architectures
  their compatibility lists name. No workflow, composite action, or script changes: CI has no libvirt daemon on the
  machine that runs the test containers, so the connection of `libvirt-outside-of-docker` to a daemon outside its
  container is tested locally only, and its `NOTES.md` states that limit and the result of the local test.
- The root `README.md` gains both features' rows in its generated list, and `README.zh.md` carries the same rows in
  Chinese.

## Capabilities

### New Capabilities

- `libvirt-outside-of-docker`: installing the libvirt client tools, the default connection, aligning the remote user
  with the group of a mounted host socket at every start, the start check, the refusal to coexist with
  `libvirt-in-docker`, and installing twice.
- `libvirt-in-docker`: installing the libvirt daemon and QEMU, starting them at every container start in a privileged
  container, the QEMU and access configuration a container needs, the default network, the persistent volumes, the start
  check, the refusal to coexist with `libvirt-outside-of-docker`, and installing twice.

### Modified Capabilities

None.

## Impact

- Feature ids touched: `libvirt-outside-of-docker` and `libvirt-in-docker`, both new at version `1.0.0`.
- Files: `src/libvirt-outside-of-docker/` and `src/libvirt-in-docker/` (each `devcontainer-feature.json`, `install.sh`,
  `scripts/`, `NOTES.md`, and `README.md` generated by `just docs`); `test/libvirt-outside-of-docker/` and
  `test/libvirt-in-docker/` (each `test.sh`, `duplicate.sh`, `scenarios.json` with its scenario scripts, and
  `compatibility.json`); the root `README.md` (its generated feature list) and `README.zh.md` (the translated rows).
- `test/canary.json` is not touched.
- Metadata of `libvirt-outside-of-docker`: `containerEnv`, `entrypoint`, and `postStartCommand`; no `mounts`,
  `privileged`, `capAdd`, `securityOpt`, `init`, `dependsOn`, or `installsAfter`.
- Metadata of `libvirt-in-docker`: `privileged`, two `mounts` (named volumes), `containerEnv`, `entrypoint`, and
  `postStartCommand`; no `capAdd`, `securityOpt`, `init`, `dependsOn`, or `installsAfter`.
- Network at build time: the image's configured package repositories only; nothing at container start.
- CI: the PR runs both features' container tests through the existing jobs; no workflow changes. The jobs of
  `libvirt-in-docker` run privileged containers, as the feature's metadata declares.
- Security: `libvirt-in-docker` runs a privileged container in which QEMU runs as root without a security driver and
  members of the `libvirt` group reach the daemon without authentication; with `libvirt-outside-of-docker`, a
  developer's mount of the host's socket gives the remote user control of the host's system daemon. The delta specs
  state both risks and their reasons.

## Acceptance

**Becomes true:**

- Every scenario in `specs/libvirt-outside-of-docker/spec.md` and `specs/libvirt-in-docker/spec.md` that a successful
  container build or a scenario script can show holds on every image and architecture in the feature's
  `compatibility.json`, exercised by `test.sh`, `duplicate.sh`, and the scenarios; every other scenario holds in the
  check design.md (Goals, Tests) names for it, run once. Each result is recorded in the PR's Validation section.
- The scenarios of `libvirt-outside-of-docker` that need a libvirt daemon outside the container hold in the local test
  design.md describes (Local end-to-end test), and `src/libvirt-outside-of-docker/NOTES.md` states that CI does not
  cover them, what the local test ran against, and its result.
- Each `compatibility.json` lists exactly the images and architectures planned in design.md (Supported images).
- Both `devcontainer-feature.json` files have version `1.0.0`, and both features' `README.md` and the root `README.md`
  are what `just docs` generates.
- `src/libvirt-outside-of-docker/NOTES.md` gives the mount to add to `devcontainer.json`, and each feature's `NOTES.md`
  states what its delta spec's requirements say `NOTES.md` states (the documented limits, host requirements or
  persistence, the accepted risks, and the path of the start record).
- `README.zh.md` holds the translated rows for both features in its feature list.
- `just test` and `just test-scenarios` pass locally for both features, and the PR's container test jobs pass on amd64
  and arm64.

**Stays true:**

- Neither feature downloads anything but packages from the repositories the image already configures, adds a repository
  or a signing key, or contacts the network at container start.
- `libvirt-outside-of-docker` declares no `mounts`, `privileged`, `capAdd`, or `securityOpt`, and never writes to,
  re-owns, or changes the mode of anything under a mounted `/run/libvirt`.
- `libvirt-in-docker` never starts a daemon while `/run/libvirt` is a mount point.
- No file outside `src/libvirt-outside-of-docker/`, `src/libvirt-in-docker/`, `test/libvirt-outside-of-docker/`,
  `test/libvirt-in-docker/`, the root `README.md`, `README.zh.md`, and this change changes; in particular nothing under
  `.github/` or `scripts/`.
- `just check` passes, and every required check passes on this PR.
