# Proposal

Implements [#59](https://github.com/hoshiori-dev/devcontainer-features/issues/59), part of the epic
[#127](https://github.com/hoshiori-dev/devcontainer-features/issues/127) (package-manager features: phase 2 controls).

## Why

After phase 1, `zypper-packages` always works with every repository the image enables, lets zypper fall back from a
package name to any package providing that name, fails at once when another process holds libzypp's lock, and downloads
with whatever timeouts and attempts the image happens to configure. A build that must not depend on one of the image's
repositories, that must not install a provider for a mistyped name, or that runs on a slow or contended network has no
way to say so short of a Dockerfile. The epic's bar is that a developer can choose among the sources the image already
provides and tune downloads, retries, and lock waiting where the package manager supports it, while a feature whose new
options are unset behaves exactly as after phase 1.

## What Changes

- `zypper-packages` gains six options, each inert at its default: `exactNames` (match entries by package name only),
  `repositories` (restrict the invocation to named repositories the image already enables), `lockTimeout`,
  `connectTimeout`, `transferTimeout`, and `downloadRetries`. Their contracts, interactions with the phase 1 options,
  refused values, and accepted risks are in the delta spec.
- An explicitly set option that the image's libzypp or the build environment cannot honor fails the feature instead of
  being ignored.
- The feature's `NOTES.md` documents what the feature sets, what it inherits from the image's zypper and libzypp
  configuration, how a proxy reaches zypper, and how locks and retries behave where no option exists.
- The Purpose of `openspec/specs/zypper-packages/spec.md` is corrected by hand in this approval package, because
  OpenSpec ignores a delta's Purpose for an existing capability: its "Upstream sources" list gains the libzypp source
  repository and the configuration files specification that zypp.conf(5) refers to, both of which the new behavior
  relies on. The Purpose's opening sentence is unchanged; it still holds.
- Not part of this change: downgrade and conflict-replacement policy (phase 3), enabling a repository the image
  disables, adding repositories, a parallel-download option, a proxy option, and the pre-existing defects listed in
  `design.md` (Follow-up work).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `zypper-packages`: repository selection, exact-name matching, lock waiting, download timeouts, and bounded retries,
  each scoped to one invocation; the validation, matching, installation, refresh, authentication, and install-twice
  requirements are extended to cover them.

## Impact

- Feature ids touched: `zypper-packages` changes from 1.0.1 to 1.1.0 (MINOR: new options, no default changed, no option
  renamed or removed). No other feature changes, and none depends on it.
- Implementation after approval: `src/zypper-packages/` (`install.sh`, `devcontainer-feature.json`, `NOTES.md`, and
  `README.md` generated by `just docs`) and `test/zypper-packages/` (scenarios and their scripts).
  `test/zypper-packages/compatibility.json` is unchanged.
- This commit carries the approval package only: the proposal, the delta spec, the design, and the Purpose correction.
  The metadata, its version, and the installer change after the package gate closes; the published 1.0.1 is not claimed
  to implement the new options.
- No script, workflow, test infrastructure, knowledge file, or devcontainer configuration changes.

## Acceptance

**Becomes true:**

- Every scenario of the delta spec's ADDED requirements ("Option exactNames", "Option repositories", "Option
  lockTimeout", "Option connectTimeout", "Option transferTimeout", "Option downloadRetries", "Repository selection
  restricts the installation", "Lock wait is scoped to installation", "Download timeouts are scoped to installation",
  "Download retries are bounded", "Timeout and retry overrides are temporary", "Image configuration and proxy are
  inherited") passes in the check `design.md` (Verification bounds) names for it, and the PR's Validation section names
  each scenario with its test, image, architecture, and result.
- Every scenario the delta spec adds to its MODIFIED requirements ("Installation controls are validated before changes",
  "Entries select packages as zypper matches them", "Repository authentication stays in effect", "Installing the feature
  twice") passes the same way.
- `src/zypper-packages/devcontainer-feature.json` has version `1.1.0` and declares exactly the options of the spec as
  archived; `just check` passes, including the option comparison of `just spec-check` and the README generated by
  `just docs`.
- `src/zypper-packages/NOTES.md` has one section on configuration with the headings "What the feature sets explicitly",
  "What is inherited", "Proxy", and "Locks and retries"; every statement in it that `design.md` marks as not verified is
  labeled as such.
- `just test zypper-packages` and `just test-scenarios zypper-packages` pass on every image and architecture of
  `test/zypper-packages/compatibility.json` that each of them covers.

**Stays true:**

- With `exactNames` at `false` and the five string options empty, the feature makes the same `zypper` calls with the
  same arguments and environment as version 1.0.1 and writes no file of its own (scenario "Undeclared settings are
  inherited"); every scenario of the main spec that this change does not rename or remove still passes.
- `packages`, `installRecommends`, `refreshPolicy`, and `cleanup` keep their names, types, defaults, and `enum` values.
- The feature never disables or weakens signature or TLS checking, never trusts a key on its own, and itself adds,
  removes, enables, or edits no repository, service, or key (scenarios under "Repository authentication stays in
  effect").
- Nothing the feature sets outlives the invocation: no environment variable, configuration file, or directory of its own
  remains in the image (scenarios "Override file is removed after success", "Override file is removed after failure",
  "Selection and network controls do not carry over").
- An empty package list with valid options succeeds without `zypper`, whatever the other options hold (scenarios "Empty
  list ignores installation controls", "Empty list ignores selection and network controls").
- The feature passes zypper nothing that lets it remove an installed package to resolve a conflict, and such a conflict
  fails the feature (requirement "Installed packages are not removed", scenario "Conflict with a package of an
  unselected repository fails"); with a non-empty `repositories` this holds within the bound that the requirement
  "Repository selection restricts the installation" states.
- The feature fetches nothing itself: `install.sh` contains no URL and no download tool.
- `devcontainer-feature.json` declares none of `privileged`, `capAdd`, `securityOpt`, `mounts`, `entrypoint`, `init`,
  `containerEnv`, lifecycle commands, `dependsOn`, or `installsAfter`.
- The images and architectures of `test/zypper-packages/compatibility.json` stay supported, and no file outside
  `src/zypper-packages/`, `test/zypper-packages/`, and `openspec/` changes.
